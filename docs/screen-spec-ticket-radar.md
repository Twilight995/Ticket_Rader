# 티켓레이더(가칭) 화면 설계 (5주차 화면 명세표)

- 작성일: 2026-10-28
- 입력 문서: `docs/prd-ticket-radar.md` 5절 화면 흐름, 4절 Won't 목록, 3.2절 선택(반응형 웹 한 벌, 텍스트+캡처 입력, 로그인 없음)
- 양식: 프로젝트관리지원기술 5주차 3부 STEP 1~4 그대로
- 화면 설계의 A: 화면 담당 (기획서 RACI "팬용 화면" R/A). 관리자 화면은 서버 담당이 쓰고 화면 담당이 모양을 맞춘다.
- AI가 추론해 채운 칸은 **부록**에 모았다. 팀이 한 번 읽고 다르면 고친다.

이 문서의 역할: 그리기 전에 글로 정한다. 이 표가 있으면 사람이 그리든 AI가 그리든 같은 화면이 나온다. 종이 와이어프레임(STEP 3)과 종이 테스트(STEP 4)는 팀이 직접 한다.

## STEP 1. 핵심 흐름 고르기

| 항목 | 내용 |
|---|---|
| **팀명** | 월32 |
| **화면 설계의 A** | 화면 담당 |
| **오늘 설계할 흐름의 목적** | 팬이 중고 판매글 하나를 결제 전에 공식 안내와 비교해 "확인이 필요한 부분"을 안다 |
| **플랫폼** (지난주 선택) | 웹, 반응형 화면 한 벌. 모바일(세로, 한 손) 기준으로 먼저 그리고 PC에서는 옆으로 펼친다 |
| **화면 순서** | ⓪ 홈 → ① 판매글 입력 → ② 추출 결과 확인 → ③ 확인사항 결과 → (④ 제보 근거 정리, Should). 별도: ⑤ 관리자 규정 재확인 (홈은 2026-11-01 Must로 추가) |
| **버튼, 입력창, 제목 모양을 정하는 사람** | 화면 담당 (아래 "공통 모양 규칙"을 먼저 정하고 나머지가 따른다) |
| **디자인 안내서** | Material Design 3 (웹이므로). AI에게 화면을 시킬 때 "Material Design 3 안내를 따를 것" 한 줄을 붙인다 |

### 공통 모양 규칙 (한 사람이 정하고 모두 따른다)

| 요소 | 규칙 |
|---|---|
| 주인공 버튼 | 화면당 1개. 화면 너비 전체(모바일) 또는 오른쪽 아래(PC). 글씨는 "누르면 일어나는 일"로 적는다. 누르면 비활성화되고 "처리 중…"으로 바뀐다 |
| 보조 버튼 | 테두리만 있는 버튼. 주인공 버튼보다 작고 옆이나 위에 둔다 |
| 입력창 | 라벨은 입력창 위에, 예시 값은 입력창 안에 회색으로. 화면당 입력 3개 이하, 나머지는 "추가 항목"으로 접어 둔다 |
| 제목 | 화면마다 제목 1줄 + 설명 1줄. 제목은 사용자가 할 일로 적는다 ("판매글을 확인해 보세요") |
| 확인사항 심각도 | 색으로만 구분하지 않는다. 글자 라벨 "정보 / 주의 / 확인 필요"를 항상 같이 붙인다 |
| 글씨 | 본문 16px 이상. 회색 배경에 연한 회색 글씨 금지 |
| 고정 문구 | 결과를 보여주는 화면 맨 아래에 항상: "이 결과는 참고용이며 최종 판단은 사용자가 합니다." |
| 금지 단어 | 화면 어디에도 "암표·암표상·불법·사기·상습" 없음. 결과 이름은 "확인이 필요한 부분" |

## STEP 2. 화면 명세표

### 화면 ① 판매글 입력

| 항목 | 내용 |
|---|---|
| **화면 이름** | 판매글 입력 |
| **누가 오는가** | 중고 티켓을 사려는 팬. 로그인 없음. ⓪ 홈에서 "판매글 확인하기"를 눌러 넘어온다 (주소로 바로 들어와도 열린다) |
| **이 화면의 목적** (한 가지) | 판매글 하나를 서비스에 넣는다 |
| **주인공 행동** | "이 판매글 확인하기" 버튼 (공연이 선택되고 글 또는 이미지가 있을 때만 활성) |
| **보여줄 정보** | 서비스 한 줄 설명("판매글을 공연 공식 안내와 비교해 드려요. 진위·불법 여부는 판단하지 않아요"), 공연 선택(공연 1건이라 기본 선택됨), 판매글 텍스트 입력칸, 캡처 이미지 올리기(PNG/JPG, 5MB 이하 안내), 올린 이미지 미리보기 |
| **보조 행동** | 캡처 이미지 삭제, 입력 내용 지우기 |
| **빈 상태** | 처음 온 상태. 입력칸 안에 예시 글("예: VIP석 2장 양도, 장당 25만, 선입금 후 QR 전송") 회색으로. 버튼은 비활성 |
| **로딩 상태** | 버튼이 "읽는 중…"으로 바뀌고 비활성. 입력칸은 잠김. 이미지 올리는 중에는 미리보기 자리에 회색 박스 |
| **오류 상태** | 이미지가 5MB 초과·형식 불일치: 이미지 칸 아래 빨간 글씨 + "다른 이미지 올리기". 서버 연결 실패: "연결하지 못했어요. 입력한 내용은 그대로 있어요" + "다시 시도" |
| **여기서 갈 수 있는 화면** | ② 추출 결과 확인 (AI 성공·실패 모두 ②로 간다. 실패하면 ②가 빈 폼으로 열린다) |
| **절대 넣지 않는 것** | 로그인·회원가입, 공연 검색(공연 1건), 다른 사이트 링크 붙여넣어 자동 수집, 광고, 최근 확인 기록 목록 |

### 화면 ② 추출 결과 확인

| 항목 | 내용 |
|---|---|
| **화면 이름** | 추출 결과 확인 |
| **누가 오는가** | ①에서 넘어온 팬 |
| **이 화면의 목적** (한 가지) | AI가 뽑은 값을 사람이 확인하고 고친다 |
| **주인공 행동** | "공식 안내와 비교하기" 버튼 (가격 또는 전달 방식 중 하나 이상 있을 때 활성) |
| **보여줄 정보** | 필수 입력 3개: 1장당 가격(원), 좌석 등급·구역, 전달 방식(선택지: 본인 현장 수령 / 캡처·QR 전송 / 계정 양도 / 모바일 티켓 전송 / 기타). 접힌 "추가 항목": 수량, 선입금 요구 여부(켜기/끄기). 각 값 옆에 AI가 근거로 삼은 판매글 구절("25만"처럼) 작은 글씨. 맨 위에 "AI가 읽은 값이에요. 틀린 곳을 고쳐 주세요" 1줄 |
| **보조 행동** | "추가 항목 펼치기", "판매글 다시 보기"(원문을 접었다 펴기), "처음부터 다시" |
| **빈 상태** | AI가 실패했을 때. 맨 위 안내 "AI가 내용을 읽지 못했어요. 아래에 직접 입력해 주세요"(오류 색이 아니라 안내 색). 입력칸은 모두 비어 있고 예시 값만 회색. 흐름은 그대로 이어진다 |
| **로딩 상태** | ①에서 넘어오는 동안: 입력칸 자리에 회색 박스 3개 + "판매글을 읽는 중…" |
| **오류 상태** | 입력값 형식 오류(가격에 글자 등): 해당 칸 아래 빨간 글씨 "숫자만 입력해 주세요". 비교 요청 실패: 버튼 아래 "비교하지 못했어요. 입력값은 그대로 있어요" + "다시 시도" |
| **여기서 갈 수 있는 화면** | ③ 확인사항 결과, ① 판매글 입력(처음부터 다시) |
| **절대 넣지 않는 것** | 판매자 연락처 입력칸(연락처는 화면에 다시 보여주지 않는다), 입력칸 6개 이상 한꺼번에 노출, "정상/비정상" 같은 판정 미리보기, 자동 저장 안내 |

### 화면 ③ 확인사항 결과

| 항목 | 내용 |
|---|---|
| **화면 이름** | 확인사항 결과 |
| **누가 오는가** | ②에서 넘어온 팬 |
| **이 화면의 목적** (한 가지) | 판매글의 어느 부분이 공식 안내와 다른지, 근거와 함께 안다 |
| **주인공 행동** | 확인사항 카드를 읽는 것 자체. 버튼으로는 "공식 안내 원문 보기"(출처 링크, 새 창) |
| **보여줄 정보** | 요약 1줄("확인이 필요한 부분 3가지를 찾았어요"). 카드마다: ① 이름(예: "정가보다 높음") + 라벨(정보/주의/확인 필요) ② 판매글 원문 구절 ③ 공식 안내 문장 ④ 출처 URL + 확인 날짜("2026-10-28 확인") ⑤ 쉬운 말 설명 1~2문장 ⑥ "예매처에 재확인하세요". 모바일은 ②③이 위아래, PC는 나란히. 맨 아래 고정 문구 |
| **보조 행동** | "다른 판매글 확인하기"(①로), "제보 자료 만들기"(④로, Should가 들어올 때만 보임), 공식 신고센터 링크 1개 |
| **빈 상태** | 확인사항 0건. "확인이 필요한 부분을 찾지 못했어요. 거래 전 예매처 규정은 꼭 확인하세요" + 공식 안내 원문 링크. **"안전합니다"라고 쓰지 않는다** |
| **로딩 상태** | 요약 자리와 카드 자리에 회색 박스 3개 + "공식 안내와 비교하는 중…" |
| **오류 상태** | "비교 결과를 불러오지 못했어요" + "다시 시도" + "입력한 값으로 돌아가기"(②로) |
| **여기서 갈 수 있는 화면** | ① 판매글 입력, ④ 제보 근거 정리(Should), 외부: 공식 안내 원문·신고센터(새 창) |
| **절대 넣지 않는 것** | "암표/불법/사기" 판정 문구, 점수·등급·신호등, 판매자 정보, 공유·캡처 저장 버튼(Should 범위), 광고, 결제·구매 버튼 |

### 화면 ④ 제보 근거 정리 (Should. Must가 끝난 뒤에만 만든다)

| 항목 | 내용 |
|---|---|
| **화면 이름** | 제보 근거 정리 |
| **누가 오는가** | ③에서 "제보 자료 만들기"를 누른 팬 |
| **이 화면의 목적** (한 가지) | 방금 본 결과를 공식 신고센터에 낼 수 있는 한 장으로 정리한다 |
| **주인공 행동** | "PDF로 저장" (브라우저 인쇄) |
| **보여줄 정보** | 공연명·확인 일시, 판매글 원문(연락처는 가려진 상태), 확인사항 대조표(판매글 구절 ↔ 공식 문장 ↔ 출처), 신고센터 링크와 제출 절차, 고정 문구 "본 자료는 공개된 공식 안내와 대조한 참고 자료이며, 위법 여부는 신고기관이 판단합니다" |

| **빈 상태** | 확인사항 0건인 글로 들어온 경우: "확인이 필요한 부분이 없어 담을 내용이 적어요" + 그래도 저장은 가능 |
| **로딩 상태** | 한 장 자리에 회색 박스 |
| **오류 상태** | "자료를 만들지 못했어요" + "다시 시도" |
| **여기서 갈 수 있는 화면** | ③ 확인사항 결과, 외부: 신고센터(새 창) |
| **절대 넣지 않는 것** | 신고 대행·자동 제출 버튼, 판매자 연락처·신원, "상습/암표상" 표현, 서비스가 대신 판단한 결론 |

### 화면 ⑤ 관리자 규정 재확인 (Must. 팬 흐름과 분리)

| 항목 | 내용 |
|---|---|
| **화면 이름** | 관리자 규정 재확인 |
| **누가 오는가** | 팀원(관리자). 별도 주소로 들어오고, 브라우저 기본 로그인창에 관리자 비밀번호 1개를 넣는다 (회원가입 없음. 6주차 아키텍처 STEP 1 "인증"에서 확정) |
| **이 화면의 목적** (한 가지) | 파일로 넣은 공연 1건의 정가표와 규정 문장이 맞는지 보고 고친다 |
| **주인공 행동** | "수정 내용 저장" |
| **보여줄 정보** | 공연명·일시·장소. 정가표: 좌석 등급 / 1장당 정가 / 출처 URL / 확인 날짜. 규정표: 규정 종류(본인 확인 필수 / 양도 금지 / 캡처 입장 불가 / 현장 수령 필수 / 기타) / 공식 문장 / 출처 URL / 확인 날짜. 각 행 수정 가능 |
| **보조 행동** | 정가 행 추가·삭제, 규정 행 추가·삭제, "변경 취소" |
| **빈 상태** | 파일이 비어 있을 때: "아직 공연 정보가 없어요. 공식 공지를 보고 첫 정가와 규정을 입력하세요" + 행 추가 버튼 |
| **로딩 상태** | 표 자리에 회색 줄 5개 |
| **오류 상태** | 저장 실패: "저장하지 못했어요. 입력값은 그대로 있어요" + "다시 시도". 출처 URL 형식 오류: 해당 칸 아래 "http로 시작하는 주소를 넣어 주세요" |
| **여기서 갈 수 있는 화면** | 없음(관리자 화면 한 장) |
| **절대 넣지 않는 것** | 공연 추가(공연 1건), 외부 공지 자동 수집 버튼, 판매글 목록·통계(Should 범위), 회원 관리 |

### 화면 ⓪ 홈 (2026-11-01 팀 결정: **Must**) · 시작 화면(스플래시, **미채택** — 범위 밖)

> 2026-11-01 팀 결정: **홈은 Must에 넣는다.** 첫 화면은 홈이고, 주인공 버튼 한 번이면 ① 판매글 입력으로 간다(로그인은 여전히 없다). 스플래시는 채택하지 않았다. pen 파일의 스플래시 그림은 참고용으로 남겨 두되 구현하지 않는다. 홈에도 피드·검색·공유·점수·광고·로그인은 넣지 않는다. 기획서 4절 Must와 5절 흐름에 홈을 추가했다.

| 항목 | 스플래시 | 홈 |
|---|---|---|
| **화면 이름** | 시작 화면 | 홈 |
| **누가 오는가** | 주소로 처음 들어온 팬(모바일 웹을 홈 화면에 추가했을 때만 뜸) | 스플래시 다음, 또는 ③에서 "다른 판매글 확인하기" |
| **이 화면의 목적** (한 가지) | 서비스 이름과 한 줄 정의를 1~2초 보여 주고 홈으로 | 무엇을 해 주는 서비스인지 알고 ①로 넘어간다 |
| **주인공 행동** | 없음(자동 전환) | "판매글 확인하기" → ① |
| **보여줄 정보** | 로고, "티켓레이더", "판매글을 공식 안내와 비교해 드려요", 고정 문구 | 제목 한 줄("티켓 판매글, 결제 전에 공식 안내와 맞춰 보세요") + 설명(진위·위법 여부는 판단하지 않음), "이렇게 확인해요" 3단계, 지금 확인할 수 있는 공연 1건(이름·일시·장소 + 공식 안내 원문 링크), 고정 문구 |
| **보조 행동** | 없음 | 공식 안내 원문 보기(새 창) |
| **빈 상태** | 없음 | 관리자가 공연을 아직 등록하지 않음: "아직 확인할 수 있는 공연이 없어요. 관리자가 공연 정보를 등록하면 시작할 수 있어요" + 주요 버튼 비활성 |
| **로딩 상태** | 화면 자체가 로딩(스피너) | 공연 카드 자리에 회색 줄(②③과 같은 부품) |
| **오류 상태** | 없음(실패하면 홈으로) | 공연 정보를 못 불러옴: 공연 카드 자리에 "불러오지 못했어요" + "다시 시도"(③과 같은 부품) |
| **여기서 갈 수 있는 화면** | 홈 | ① 판매글 입력, 외부: 공식 안내 원문 |
| **절대 넣지 않는 것** | 광고, 약관 동의 모달, 로그인 | 피드·검색·공유·점수·광고·로그인, 판매글 목록, "안전" 표현 |

## STEP 3. 종이 와이어프레임 (팀이 직접)

2026-10-28 추가: 이 명세표를 그대로 옮긴 저해상도 와이어프레임을 `docs/ticket_rader_mock.pen`(pen.dev)에 그려 두었다. 화면 ①②③은 네 가지 상태 네 장씩(③은 PC 1024px 한 장 더), 화면 ⑤는 정상·빈 상태 두 장, 합계 15장. 종이로 다시 그릴 필요는 없고, 종이 테스트(STEP 4)는 이 화면을 인쇄하거나 화면에 띄워서 한다.

2026-11-01 추가: 같은 pen 파일 아래쪽에 **상세 디자인(다크·라이트 두 모드)** 을 그렸다. 부품판(디자인 시스템) + 모바일 390: ① 다섯 장(오류를 이미지 오류/연결 실패로 나눔) + ② 다섯 장(오류를 입력 형식/비교 실패로 나눔) + ③ 네 장 + ⑤ PC 정상·빈 상태 두 장. PC 1024는 별도 묶음: 홈 2장 + ①②③ 정상·빈·로딩·오류 14장(머리줄 단계 표시 + 작업 616/참고 320 두 단) + ⑤ 로딩·오류 2장, 해상도 샘플(768 태블릿·1440 큰 PC) 5장. 모두 다크·라이트 두 모드. 색·크기·규칙은 `docs/design-tokens.md`, 참고한 Suno 관찰은 `docs/suno-ui-reference.md`, 외부 검토 반영은 `docs/suno-design-review-2026-11-01.md`에 있다. 종이 테스트는 와이어프레임 15장으로 하고, 상세 디자인은 구현 때 기준으로 쓴다.

2부 3번 규칙대로 그린다. 세로 스마트폰 네모를 먼저 그리고, PC는 같은 요소를 옆으로 펼친 한 장만 더 그린다.

- 화면 ①②③은 각각 **네 가지 상태 네 장**, 화면 ⑤는 정상·빈 상태 두 장. 화면 ④는 Should라 그리지 않는다.
- 버튼 글씨는 위 명세표의 실제 문구를 그대로 쓴다. "확인", "제출"이라고 쓰지 않는다.
- 화면 밖으로 나가는 화살표에 어느 화면으로 가는지 적는다.
- 다 그리면 사진을 찍어 팀 페이지에 올린다. 6주차 데이터 설계에서 "보여줄 정보" 줄과 함께 쓴다.

AI에게 화면 초안을 시킬 때는 이 문서의 명세표 한 장을 그대로 붙여넣고 마지막에 한 줄만 붙인다:

```
위 화면 명세표대로만 그릴 것. "절대 넣지 않는 것"은 넣지 말 것. 네 가지 상태를 각각 그릴 것. Material Design 3 안내를 따를 것.
```

AI 결과에서 사람이 볼 것 세 가지: ① 넣지 말라고 한 적 없는데 넣은 것(필터, 추천, 공유, 점수) ② 빠진 상태(빈·오류) ③ 버튼 문구가 "확인/제출"로 바뀌었는지.

## STEP 4. 종이 테스트

다른 팀 한 명에게 종이를 순서대로 놓고 과제 한 문장만 준다. **설명하지 않는다.**

| 과제 문장 | 기대하는 경로 |
|---|---|
| "이 판매글(가상 글 1장 건넴)이 공식 안내와 맞는지 확인해 보세요" | ① 붙여넣기 → 버튼 → ② 값 확인 → 버튼 → ③ 카드 읽기 |
| "가격이 잘못 읽혔어요. 고쳐서 다시 확인해 보세요" | ②에서 가격 수정 → 버튼 → ③ |
| "확인사항이 하나도 없다고 나오면 이 글은 안전한 건가요?" (질문만 던진다) | ③ 빈 상태의 문구만 보고 "아니요, 예매처 규정을 확인하라고 한다"고 답하면 통과 |

| 화면 | 테스트한 사람이 멈춘 곳 / 잘못 누른 곳 / 물어본 것 | 왜 그러는 것 같은가 | 어떻게 고칠 것인가 |
|---|---|---|---|
| | | | |
| | | | |
| | | | |

> 테스트한 사람이 헤매면 그 사람 탓이 아니라 화면 탓이다. 설명하고 싶어지는 자리가 곧 고칠 자리다.
