# 티켓레이더 설계 명세서

- 작성일: 2026-10-16 (v2: 상습 판매자 추적·신고 자료 묶음 추가, 브라우저 확장은 선택)
- 대상: 2026 AID AI-THON 출품작 (동작 데모 필수)
- 팀: 2~3명, 개발 기간 2~4주
- 상태: 설계 승인됨 (B안 + A 확장)

## 1. 한 줄 정의

팬이 중고 티켓 판매글을 붙여넣으면, AI가 가격·좌석·수량·전달 방식을 뽑아내고, 그 공연의 공식 정가·입장 규정과 대조해 "확인이 필요한 점"을 판매글 원문과 공식 출처와 함께 보여준다. 팬들이 올린 판매글은 **판매자 지문**으로 연결되어 "같은 연락처의 글이 여러 공연에 반복 게시됨" 같은 상습성 근거가 쌓이고, 팬은 버튼 하나로 **공식 신고센터에 낼 신고 자료 묶음**을 만든다. 암표·사기 여부는 확정하지 않고, 최종 판단은 사람(팬·담당자·신고기관)이 한다.

## 2. 배경과 위치

### 2.1 법 환경 (2026년 10월 기준)

- 2026년 8월 말 시행된 개정 공연법은 매크로 사용 여부와 관계없이 "최초 판매자 동의 없이 **상습 또는 영업으로** 구입가보다 비싸게 되파는 행위"를 부정판매로 규정하고, 판매액의 2배~최대 50배 과징금과 **신고포상금**(부정구매 신고 최대 5천만 원, 부정판매 신고는 과징금의 50% 범위)을 도입했다.
- 1회성 양도, 구입가 이하 양도는 부정판매가 아니다. 웃돈을 주고 산 사람도 처벌 대상이 아니다.
- 따라서 처벌 여부를 가르는 핵심은 가격이 아니라 **상습성·영업성**이다. 그런데 팬 한 명이 보는 판매글 한 건으로는 상습성을 알 수 없고, 신고하려면 증거를 직접 모아야 한다. 이 빈자리가 이 서비스의 자리다.
- 이 서비스는 가격이나 반복 게시만으로 "암표"나 "불법"을 확정하지 않는다. 결과 명칭은 항상 **"검토가 필요한 매물"** 이고, 상습성도 "같은 지문의 글이 N건 확인됨"이라는 사실만 보여준다.

### 2.2 기존 서비스와의 차이

| 기존 | 성격 | 우리와의 차이 |
|---|---|---|
| 음공협 SMAIT (AI·OCR 모니터링) | 기관이 플랫폼·SNS를 사후 감시 | 팬이 결제 전에 눈앞의 글을 확인하는 용도가 아님 |
| 프로스포츠 암표신고센터, KOCCA 신고센터 | 신고 접수 + 예매처 전달 | 신고서를 팬이 직접 써야 하고, 상습성 근거를 모아 주지 않음 |
| 티켓베이 입장 안심 서비스 | 입장 거부 시 환불 보상 | 거래 성립 이후의 보상 |

차별점 두 가지:
1. **결제 전, 근거가 보이는 확인**: 판매글 문구와 공식 공지 문장을 나란히 놓고 출처·확인 시각과 함께 보여준다.
2. **팬 집단이 만드는 상습성 근거 + 한 번에 만드는 신고 자료**: 법이 요구하는 바로 그 증거를 팬 제보로 쌓고, 신고와 포상금으로 이어지는 길을 연다.

### 2.3 하지 않는 것 (발표에서 선을 긋는 문장)

- 티켓 진위 인증, 입장 보장
- 사기·암표·상습 여부 확정 (사실의 개수만 보여준다. 법적 판단은 신고기관·수사기관이 한다)
- 판매자 신원 공개, 판매자 명단 공개 (사적 제재 금지)
- 신고 대행 (자료만 만들고 제출은 팬이 공식 신고센터에 직접 한다)
- 예매처 결제 명의 대조 (외부에서 조회 불가. "예매처 연동 시 확장 가능"으로 장표 한 줄만 둔다)
- 서버에서 외부 사이트 자동 수집 (이용약관·법 위험)

## 3. 사용자와 흐름

### 3.1 사용자

| 역할 | 누구 | 하는 일 |
|---|---|---|
| 팬 | 중고 티켓을 사려는 사람 | 판매글 붙여넣기 → 추출 결과 수정 → 신호 카드 확인 → (필요 시) 신고 자료 묶음 생성 |
| 담당자 | 공연 주최·기획사 모니터링 담당 (데모에서는 팀원이 연기) | 공연별 매물·판매자 지문별 묶음 확인, 검토·신고 상태 변경 |

### 3.2 핵심 흐름

```
판매글 입력 (텍스트, 선택: 캡처)
  → AI 구조화 추출 (가격·좌석·수량·전달 방식·선입금·연락처)
  → 연락처는 해시(지문)로 바꾸고 원문에서는 마스킹   ← 개인정보 원문 저장 금지
  → 팬이 추출 결과 수정
  → 규칙 엔진 판정 (코드, 재현 가능) + 판매자 지문 연결 (같은 해시·유사 문구)
  → 신호 카드 표시 (판매글 구절 ↔ 공식 공지 + 출처 + 확인 시각, 같은 지문 글 N건)
  → [신고 자료 만들기] → 인쇄용 신고 자료 페이지 → 팬이 공식 신고센터에 직접 제출
  → 매물 저장 → 담당자 대시보드 (공연별·판매자 지문별)
```

AI와 코드의 역할 분리:

| 단계 | 담당 | 이유 |
|---|---|---|
| 비정형 글에서 항목·연락처 뽑기 | LLM (구조화 출력) | 규칙으로 못 잡는 표현 다양성 |
| 캡처 이미지 읽기 (선택 기능) | LLM 이미지 입력 | 별도 OCR 불필요 |
| 배율 계산, 신호 판정, 지문 연결 | 코드 | 같은 입력이면 같은 결과, 테스트 가능 |
| 충돌 이유를 쉬운 말로 설명 | LLM | 규칙 결과와 공식 문장을 받아 문장만 생성 |

## 4. 화면

### 4.1 판매글 검사 (팬용, `/check`)

1. 입력: 텍스트 영역, 공연 선택 드롭다운. 캡처 업로드(PNG/JPG, 5MB 이하)는 선택 기능으로 후순위.
2. 추출 결과 폼: 가격(1장당, 원), 좌석 등급/구역, 수량, 전달 방식(본인 현장 수령/캡처·QR 전송/계정 양도/모바일 티켓 전송/기타), 선입금 요구 여부, 연락 채널 종류(전화/계좌/오픈채팅/텔레그램/기타 — 값 자체는 화면에 다시 보여주지 않음), 원문 구절. 모든 값 수정 가능.
3. 신호 카드 목록: 카드마다 ① 신호 이름 ② 판매글 원문 구절 ③ 공식 공지 문장 + 출처 URL + 확인 시각 ④ 쉬운 말 설명 ⑤ "예매처에 재확인하세요".
4. **판매자 지문 줄**: "같은 연락처로 올라온 판매글이 다른 공연 N건, 총 M장 확인됨" (0건이면 표시하지 않음). 판매자 정보는 어떤 형태로도 보여주지 않는다.
5. **[신고 자료 만들기]** 버튼 → 4.4 페이지로 이동.
6. 하단: 공식 신고센터 링크(공연: KOCCA 신고센터, 스포츠: 프로스포츠 암표신고센터), 포상금 제도 안내 한 줄, "이 결과는 참고용이며 최종 판단은 사용자가 합니다" 고정 문구.

### 4.2 담당자 대시보드 (`/dashboard`)

1. 공연 선택.
2. 요약 타일: 매물 수, 정가 초과 매물 비율, 검토 대기 수, 판매자 지문 묶음 수.
3. 정가 대비 배율 분포 차트(히스토그램, 5구간).
4. 탭 A "매물": 등록 시각, 좌석, 가격, 배율, 신호 개수, 검토 상태(대기/확인함/문제없음). 행 클릭 → 신호 카드 상세.
5. 탭 B "판매자 지문": 지문 ID(무작위 코드), 연결 근거(연락처 일치 / 문구 유사), 올린 공연 수, 매물 수, 총 수량, 정가 초과 건수, 첫·마지막 게시일, 신고 상태(미생성/자료 생성됨/접수 확인됨 — 담당자가 수동 변경). 행 클릭 → 묶인 매물 목록.
6. 반복 게시 묶음(문구 유사도)은 탭 B 안의 연결 근거로 흡수.

### 4.3 공연·규정 데이터

화면 없이 seed 파일(`events.json`)로만 넣는다. 등록 화면은 범위 밖(발표에서 "주최 측 입력 화면은 확장"으로 언급). 정가표와 규정 문장은 실제 공개 공지를 옮겨 적고 출처 URL과 확인 시각을 기록한다.

### 4.4 신고 자료 페이지 (`/report/:listingId`, 인쇄용)

브라우저 인쇄(PDF로 저장)에 맞춘 한 장짜리 페이지. 내용:

1. 요약: 공연명, 검사 일시, 신호 개수
2. 판매글 원문 (연락처 마스킹된 상태)
3. 추출 항목 표
4. 신호별 대조표: 판매글 구절 ↔ 공식 공지 문장 ↔ 출처 URL·확인 시각
5. 같은 지문 매물 목록: 공연명, 게시일, 가격, 수량, 배율만 (연락처·판매자 정보 없음)
6. 관련 법 조문 요지와 링크 (공연법 제4조의2 등), 신고포상금 안내
7. 신고센터 링크와 제출 절차
8. 고정 문구: "본 자료는 사용자가 입력한 판매글과 공개된 공식 안내를 대조한 참고 자료이며, 위법 여부는 신고기관이 판단합니다."

### 4.5 반응형

PC 기준으로 만들고 모바일(390px)에서 검사 화면이 세로로 쌓이도록 한다. 대시보드는 태블릿 이상 기준. 신고 자료 페이지는 A4 인쇄 기준.

## 5. 판별 규칙 (신호)

모든 신호는 `{ code, severity, listingQuote, evidence: { ruleText, sourceUrl, checkedAt } | null, explanation, meta? }` 형태. 근거(evidence)가 없는 신호는 출처 칸에 "일반 주의"라고 적는다. 심각도는 `info`(정보) / `caution`(주의) / `check`(확인 필요).

| 코드 | 이름 | 조건 | 심각도 | 근거 |
|---|---|---|---|---|
| PRICE_ABOVE_FACE | 정가 초과 | 가격 ÷ 해당 등급 정가 > 1.0 (배율 표시) | 1.0~1.5 주의, 1.5 초과 확인 필요 | 정가표 (출처·확인 시각 포함) |
| PRICE_UNKNOWN_SEAT | 정가 대조 불가 | 좌석 등급을 정가표와 못 맞춤 | 정보 | 없음 |
| PREPAYMENT | 선입금 요구 | `prepaymentRequested = true` | 확인 필요 | 일반 주의 |
| DELIVERY_CONFLICT | 전달 방식 충돌 | 전달 방식이 공연 규정 태그와 충돌. 우선순위 높은 규정 1개만 근거로 표시 | 확인 필요 | 공식 규정 문장 |
| TRANSFER_PROHIBITED | 양도 금지 공연 | 공연에 양도 금지 규정이 있음 | 확인 필요 | 공식 규정 문장 |
| BULK_QUANTITY | 대량 판매 | 수량 ≥ 설정값(기본 4) | 주의 | 일반 주의 |
| REPEATED_POST | 반복 게시 | 같은 공연의 다른 매물과 문장 유사도 ≥ 0.8 | 주의 | 비교 대상 매물 ID |
| OFF_PLATFORM_CONTACT | 외부 채널 유도 | 오픈채팅·텔레그램 등 외부 연락처 포함 | 정보 | 일반 주의 |
| **SELLER_PATTERN** | **같은 지문 반복** | 같은 판매자 지문의 매물이 설정값 이상 (기본: 매물 3건 이상 또는 공연 2건 이상) | 주의 (공연 2건 이상이면 확인 필요) | 지문 묶음 통계 (`meta.fingerprintId`, `meta.listingCount`, `meta.eventCount`, `meta.totalQuantity`) |

규칙 세부:

- 모든 기준값은 `rules.config.ts`에 둔다. 코드에 숫자를 박지 않는다.
- 문장 유사도: 공백·구두점 제거 후 글자 2-gram 자카드 유사도. 외부 라이브러리 없음.
- 신호 코드 1종당 카드 최대 1장.
- 정가 이하 1회 양도(양도 금지 규정 없는 공연)는 신호 0개, 지문 연결 0건이어야 한다. 이 사례를 테스트와 발표에 반드시 포함한다.
- SELLER_PATTERN의 설명 문구는 "같은 연락처로 올라온 판매글이 N건 확인되었습니다. 상습 여부는 신고기관이 판단합니다" 형식. "상습 판매자"라는 단정 표현 금지.

## 6. 판매자 지문 설계

### 6.1 지문 재료

| 재료 | 처리 | 연결 강도 |
|---|---|---|
| 전화번호, 계좌번호, 오픈채팅 링크, 텔레그램 ID | 정규화(숫자만, 소문자) 후 **비밀 솔트 + SHA-256 해시**. 원문은 저장하지 않음 | 강함 (같은 해시 = 같은 묶음) |
| 판매글 문구 | 2-gram 자카드 유사도 ≥ 0.8 | 약함 (묶음 안 "유사 글" 표시만, 묶음 병합은 하지 않음) |
| 캡처 이미지 (선택) | 범위 밖. 확장안으로만 언급 | - |

### 6.2 묶음 규칙

- 연락처 해시가 하나라도 같으면 같은 묶음(유니온-파인드: 연결된 것끼리 모두 한 묶음).
- 묶음 ID는 무작위 코드(예: `FP-7K3Q`)로 표시한다. 해시 값 자체는 화면에 내지 않는다.
- 묶음 통계: 매물 수, 공연 수, 총 수량, 정가 초과 매물 수, 첫·마지막 게시일.
- 팬 화면에는 "다른 공연 N건, 총 M장"만 보이고, 묶음 ID·매물 목록은 담당자 화면과 신고 자료에만 나온다.

### 6.3 개인정보 보호 (설계의 핵심 부분, 발표 장표 1장)

- 연락처 원문은 추출 직후 해시로 바꾸고 즉시 버린다. 판매글 원문도 저장 전에 정규식으로 마스킹한다.
- 솔트는 환경 변수(`FINGERPRINT_SALT`)로만 두고 저장소에 올리지 않는다. 솔트가 바뀌면 기존 지문과 연결되지 않는다(의도된 동작).
- 보관 기간: 매물·지문 90일(`RETENTION_DAYS`), 정리 스크립트 제공.
- 판매자 신원(이름·아이디·사진)은 어떤 형태로도 저장·표시하지 않는다.
- 신고 자료의 지문 매물 목록에는 공연·날짜·가격·수량만 들어간다.

## 7. AI 사용 설계

- 호출 위치: 서버만. 클라이언트에 API 키를 두지 않는다.
- SDK: `@anthropic-ai/sdk` (TypeScript). 원시 HTTP 호출 금지.
- 모델: `claude-opus-5-5` (기본). 환경 변수 `ANTHROPIC_MODEL`로 교체 가능(예: `claude-haiku-5-5`). 선택은 팀 결정.
- 추출 호출: `output_config.format`(구조화 출력)으로 아래 스키마의 JSON만 받는다. `client.messages.parse()` 헬퍼 사용. 어시스턴트 프리필·강제 도구 선택은 쓰지 않는다(현행 모델에서 400 오류). 비용 조절은 `output_config.effort: "low"`.
- 판매글은 구분 태그로 감싸 "분석할 자료"로만 취급한다(프롬프트 인젝션 대비).
- 설명 생성 호출: 규칙 결과 + 공식 문장 → 쉬운 말 2문장 이내, 법적 단정 표현 금지. 금지 표현 검사기를 통과하지 못하면 템플릿 문장으로 교체.
- 실패 처리: API 오류·타임아웃·`refusal` → 빈 폼을 열어 팬이 직접 입력. 서비스는 AI 없이도 끝까지 동작한다.
- 비용 상한: 요청당 `max_tokens` 2048. 입력 해시 24시간 캐시.

추출 스키마 (Zod, shared 패키지):

```ts
{
  price: number | null,            // 1장당 원 단위 정수
  seatLabel: string | null,
  quantity: number | null,
  deliveryMethod: "onsite_pickup" | "screenshot_qr" | "account_transfer" | "mobile_transfer" | "other" | null,
  prepaymentRequested: boolean,
  contacts: { type: "phone" | "bank" | "openchat" | "telegram" | "other", value: string }[],  // 서버에서 즉시 해시 후 버림
  quotes: { field: string, text: string }[]
}
```

## 8. 데이터 모델 (SQLite)

```
events               id, name, category(performance|sports), startsAt, venue, organizer, createdAt
price_tiers          id, eventId, tierName, facePrice, sourceUrl, checkedAt
rules                id, eventId, type(identity_required|transfer_prohibited|screenshot_entry_banned|onsite_pickup_required|other),
                     text, sourceUrl, checkedAt
listings             id, eventId, rawText(마스킹됨), extracted(JSON, contacts 제외), signals(JSON),
                     priceRatio, fingerprintId(nullable), reviewStatus(pending|reviewed|cleared), createdAt
contact_hashes       id, listingId, type, hash            -- 원문 없음
fingerprints         id(무작위 코드), reportStatus(none|generated|filed), createdAt, updatedAt
ai_cache             inputHash, response(JSON), createdAt
```

- `fingerprints`는 연락처 해시로 묶인 결과를 담는다. 새 매물이 들어올 때 해시가 겹치는 기존 묶음이 있으면 합친다.
- 샘플 데이터: 공연 2건(콘서트 1, 스포츠 1), 매물 약 50건. 구성: 정상 양도(정가 이하 1회) 20%, 웃돈만 20%, 선입금 15%, 규정 충돌 15%, 반복 게시 10%, **같은 지문이 여러 공연에 걸친 묶음 2개(합계 20%)**. 모두 팀이 직접 쓴 가상 글이며 연락처도 가상 번호(010-0000-xxxx 대역)를 쓴다.

## 9. API

| 메서드 | 경로 | 인증 | 역할 |
|---|---|---|---|
| GET | /api/events | 공개 | 공연 목록(정가표·규정 포함) |
| POST | /api/extract | 공개 | 텍스트(선택: 이미지) → 추출 JSON (AI). 연락처는 서버에서 해시 후 응답에는 종류만 |
| POST | /api/listings | 공개 | 수정된 추출 결과 저장 + 규칙 판정 + 지문 연결 + 설명 생성 → 신호·지문 요약 포함 매물 |
| GET | /api/listings/:id/report | 공개 (매물 ID를 아는 사람) | 신고 자료 데이터 |
| GET | /api/events/:id/listings | 담당자 | 매물 목록 + 분포 + 요약 |
| GET | /api/events/:id/fingerprints | 담당자 | 지문 묶음 목록 + 통계 |
| PATCH | /api/listings/:id/review | 담당자 | 검토 상태 변경 |
| PATCH | /api/fingerprints/:id/report-status | 담당자 | 신고 상태 변경 |

- 모든 입력은 Zod로 검증. 응답은 `{ ok, data, error }` 하나로 통일.
- 속도 제한: 추출은 IP당 분당 10회.
- 담당자 인증은 환경 변수 비밀번호의 HTTP Basic. 실제 권한 체계(RBAC)는 확장안.

## 11. 선택 확장: 브라우저 확장 프로그램 (B)

모든 필수 작업이 끝난 뒤 시간이 남으면 붙인다.

- Chrome 확장(Manifest V3). 지원 사이트 1곳만(예: 번개장터 웹 판매글 페이지).
- 사용자가 보고 있는 판매글 페이지의 본문을 콘텐츠 스크립트가 읽어 `/api/extract` → `/api/listings`로 보내고, 결과 카드를 페이지 위에 띄운다.
- 서버가 사이트를 긁지 않는다. 사용자 본인 브라우저가 보고 있는 화면만 읽는다. 발표에서 이 선을 명확히 말한다.
- 공연 선택은 확장 팝업에서 한다(자동 매칭은 확장안).
- 이 기능이 없어도 발표는 성립한다. 있으면 시연 첫 장면으로 쓴다.

## 12. 테스트

- 규칙 엔진: 신호 9종 각각 발생/미발생, 정가 이하 1회 양도는 신호 0개, 기준값 변경 반영, 시연 글 고정 결과.
- 지문: 같은 전화번호 → 같은 묶음, 다른 번호 → 다른 묶음, A-B 공유·B-C 공유 → 한 묶음, 해시가 저장소에 원문을 남기지 않음, 솔트가 다르면 해시가 다름.
- 유사도, 마스킹: 기존과 동일 (날짜·가격·좌석은 지우지 않음).
- 금지 표현 검사: "상습 판매자", "암표상", "불법" 등 단정 표현이 화면 문구·템플릿·AI 설명에 없음.
- API: Zod 실패 400, 담당자 API 인증 401, 신고 자료 응답에 연락처·해시가 없음.
- E2E 1개: 샘플 글 입력(API 키 없이) → 카드 3장 + 지문 줄 → 신고 자료 페이지 열림 → 대시보드 지문 탭에 묶음 표시.
- 목표 커버리지: 서버 `rules/`, `fingerprint/`, `lib/` 80% 이상.

## 13. 일정 (3주 기준)

| 주 | 데이터·규칙 담당 | 화면 담당 | AI·발표 담당 |
|---|---|---|---|
| 1 | 공연 2건 규정·정가 입력, 규칙 엔진 9종 + 지문 묶음 + 테스트 | 프로젝트 뼈대, 검사 화면 입력·추출 폼 | 추출 프롬프트(연락처 포함)·스키마, 캐시, 설명 생성 |
| 2 | 샘플 매물 50건(지문 묶음 2개 포함), API, seed | 신호 카드 + 지문 줄, 대시보드 매물·지문 탭, 신고 자료 페이지 | 실패 처리, 금지 표현 검사, Docker |
| 3 | 검증표(잡은 사례·안 잡은 사례·지문 묶음) | 다듬기, E2E, (여유 시) 브라우저 확장 | 발표 자료, 시연 대본, 개인정보 설계 장표, 배포 점검 |

2명일 때는 AI·발표를 둘이 나눈다. 일정이 밀리면 캡처 입력 → 브라우저 확장 → 대시보드 분포 차트 순으로 뺀다. 규칙 엔진·지문·신고 자료·신호 0개 사례·마스킹은 빼지 않는다.

## 14. 발표 시연 대본 (5분)

1. 문제: 실제 사례 수치(20만 원 티켓이 500만 원) + 개정 공연법 요지(상습·영업성, 신고포상금) 30초.
2. 팬 화면: 선입금 + QR 캡처 판매글 붙여넣기 → 추출 → 카드 3장(정가 2.5배, 선입금, 현장 수령 규정 충돌) → 출처·확인 시각 강조.
3. **지문 줄**: "같은 연락처로 올라온 판매글이 다른 공연 3건, 총 14장 확인됨" → 상습성 근거가 팬 제보로 쌓이는 구조 설명.
4. **[신고 자료 만들기]** → 인쇄용 페이지 → 법 조문·신고센터·포상금 안내까지 한 장. "제출은 팬이 공식 창구에 직접."
5. 반례: 정가 이하 1회 양도 글 → 신호 0개, 지문 연결 없음. "법이 허용하는 양도는 막지 않는다."
6. 담당자 화면: 지문 탭에서 묶음 2개, 공연별 분포, 신고 상태.
7. 개인정보 설계 장표: 원문 저장 없음, 솔트 해시, 90일 보관, 신원 비공개.
8. 한계와 확장: 브라우저 확장(있으면 시연 첫 장면으로), 예매처 연동, 이미지 지문, 공개 암표 지수.

| 위험 | 대응 |

| 일정 초과 | 캡처 입력·브라우저 확장·분포 차트 순으로 제외 |
