# 티켓레이더 설계 명세서

- 작성일: 2026-10-16
- 대상: 2026 AID AI-THON 출품작 (동작 데모 필수)
- 팀: 2~3명, 개발 기간 2~4주
- 상태: 설계 승인됨 (B안: 판매글 검사기 + 공연별 감시 대시보드)

## 1. 한 줄 정의

팬이 중고 티켓 판매글을 붙여넣으면, AI가 가격·좌석·수량·전달 방식을 뽑아내고, 그 공연의 공식 정가·입장 규정과 대조해 "확인이 필요한 점"을 판매글 원문과 공식 출처와 함께 보여준다. 모인 매물은 공연별 감시 화면에서 가격 흐름과 반복 게시로 다시 본다. 최종 판단은 사람이 한다.

## 2. 배경과 위치

### 2.1 법 환경 (2026년 10월 기준)

- 2026년 8월 말 시행된 개정 공연법은 매크로 사용 여부와 관계없이 "최초 판매자 동의 없이 상습 또는 영업으로 구입가보다 비싸게 되파는 행위"를 부정판매로 규정하고, 판매액의 2배~최대 50배 과징금과 신고포상금을 도입했다.
- 1회성 양도, 구입가 이하 양도는 부정판매가 아니다. 웃돈을 주고 산 사람도 처벌 대상이 아니다.
- 따라서 이 서비스는 가격이나 반복 게시만으로 "암표"나 "불법"을 확정하지 않는다. 결과 명칭은 항상 **"검토가 필요한 매물"** 이다.

### 2.2 기존 서비스와의 차이

| 기존 | 성격 | 우리와의 차이 |
|---|---|---|
| 음공협 SMAIT (AI·OCR 모니터링) | 기관이 플랫폼·SNS를 사후 감시 | 팬이 결제 전에 눈앞의 글을 확인하는 용도가 아님 |
| 프로스포츠 암표신고센터, KOCCA 신고센터 | 신고 접수 + 예매처 전달 | 왜 위험한지 근거를 팬에게 설명하지 않음 |
| 티켓베이 입장 안심 서비스 | 입장 거부 시 환불 보상 | 거래 성립 이후의 보상 |

차별점: **결제 전, 근거가 보이는 확인**. 판매글 문구와 공식 공지 문장을 나란히 놓고 "무엇이 충돌하는지"를 출처·확인 시각과 함께 보여준다.

### 2.3 하지 않는 것 (발표에서 선을 긋는 문장)

- 티켓 진위 인증
- 입장 보장
- 사기·암표 여부 확정
- 예매처 결제 명의 대조 (외부에서 조회 불가. "예매처 연동 시 확장 가능"으로 장표 한 줄만 둔다)
- 외부 사이트 자동 수집 (이용약관·법 위험, 데모 설득력 저하)

## 3. 사용자와 흐름

### 3.1 사용자

| 역할 | 누구 | 하는 일 |
|---|---|---|
| 팬 | 중고 티켓을 사려는 사람 | 판매글 붙여넣기 → 추출 결과 수정 → 신호 카드 확인 |
| 담당자 | 공연 주최·기획사 모니터링 담당 (데모에서는 팀원이 연기) | 공연별 매물 목록·분포 확인, 검토 상태 변경 |

### 3.2 핵심 흐름

```
판매글 입력 (텍스트 또는 캡처)
  → AI 구조화 추출 (가격·좌석·수량·전달 방식·선입금 문구·연락 채널)
  → 팬이 추출 결과 수정 (AI 오류는 사람이 고친다)
  → 규칙 엔진 판정 (코드, 재현 가능)
  → 신호 카드 표시 (판매글 원문 구절 ↔ 공식 공지 문장 + 출처 URL + 확인 시각)
  → 매물 저장 → 공연별 감시 대시보드에 반영
```

AI와 코드의 역할 분리:

| 단계 | 담당 | 이유 |
|---|---|---|
| 비정형 글에서 항목 뽑기 | LLM (구조화 출력) | 규칙으로 못 잡는 표현 다양성 |
| 캡처 이미지 읽기 | LLM 이미지 입력 | 별도 OCR 불필요 |
| 배율 계산, 신호 판정 | 코드 (규칙 엔진) | 같은 입력이면 같은 결과, 테스트 가능 |
| 충돌 이유를 쉬운 말로 설명 | LLM | 규칙 결과와 공식 문장을 받아 문장만 생성 |

심사 질문 "AI가 틀리면?"에 대한 답: 추출은 팬이 화면에서 수정하고, 판정은 규칙이라 재현된다.

## 4. 화면

### 4.1 판매글 검사 (팬용, `/check`)

1. 입력: 텍스트 영역 + 이미지 업로드(PNG/JPG, 5MB 이하). 공연 선택 드롭다운(등록된 공연 중 선택).
2. 추출 결과 폼: 가격(원), 좌석 등급/구역, 수량, 전달 방식(선택지: 본인 현장 수령/캡처·QR 전송/계정 양도/모바일 티켓 전송/기타), 선입금 요구 여부, 연락 채널, 원문 구절(각 항목이 어느 문장에서 나왔는지). 모든 값 수정 가능.
3. 신호 카드 목록: 카드마다 ① 신호 이름 ② 판매글 원문 구절 ③ 공식 공지 문장 + 출처 URL + 확인 시각 ④ 쉬운 말 설명 ⑤ "예매처에 재확인하세요" 안내.
4. 하단: 공식 신고센터 링크(공연: KOCCA 신고센터, 스포츠: 프로스포츠 암표신고센터). "이 결과는 참고용이며 최종 판단은 사용자가 합니다" 고정 문구.

### 4.2 공연 감시 대시보드 (담당자용, `/dashboard`)

1. 공연 선택.
2. 요약 타일: 매물 수, 정가 초과 매물 비율, 검토 대기 수.
3. 정가 대비 배율 분포 차트(히스토그램, 구간: ≤1.0 / 1.0~1.5 / 1.5~2.0 / 2.0~3.0 / 3.0+).
4. 매물 목록 표: 등록 시각, 좌석, 가격, 배율, 신호 개수, 검토 상태(대기/확인함/문제없음). 행 클릭 시 신호 카드 상세.
5. 반복 게시 묶음: 문장 유사도가 기준 이상인 매물을 한 그룹으로 표시.

### 4.3 공연·규정 등록 (`/admin/events`)

1. 공연 기본 정보: 이름, 일시, 장소, 주최.
2. 정가표: 좌석 등급별 정가 (여러 행).
3. 공식 규정 문장: 전달·양도·본인 확인·현장 수령 관련 공지 문장을 한 줄씩, 출처 URL과 확인 시각을 함께 입력. 각 문장에 규정 유형 태그(본인 확인 필수 / 양도 금지 / 캡처 입장 불가 / 현장 수령 필수 / 기타).
4. 데모에서는 공연 2건을 seed 파일로 미리 넣는다.

### 4.4 반응형

PC 기준으로 만들고 모바일(390px)에서 검사 화면이 세로로 자연스럽게 쌓이도록 한다. 대시보드는 태블릿 이상 기준.

## 5. 판별 규칙 (신호)

모든 신호는 `{ code, severity, listingQuote, evidence: { ruleText, sourceUrl, checkedAt } | null, explanation }` 형태를 가진다. 근거(evidence)가 없는 신호는 공식 공지가 아닌 "일반 주의 사항"으로 표시하고 출처 칸에 "일반 주의"라고 적는다.

| 코드 | 이름 | 조건 | 심각도 | 근거 |
|---|---|---|---|---|
| PRICE_ABOVE_FACE | 정가 초과 | 가격 ÷ 해당 등급 정가 > 1.0 (배율도 함께 표시) | 배율 1.0~1.5 주의, 1.5 초과 확인 필요 | 공연 정가표 |
| PRICE_UNKNOWN_SEAT | 정가 대조 불가 | 좌석 등급을 정가표와 못 맞춤 | 정보 | 없음 |
| PREPAYMENT | 선입금 요구 | 추출 결과 `prepaymentRequested = true` | 확인 필요 | 일반 주의 |
| DELIVERY_CONFLICT | 전달 방식 충돌 | 전달 방식이 공연 규정 태그와 충돌 (예: 캡처·QR 전송 vs 현장 수령 필수 / 본인 확인 필수) | 확인 필요 | 공식 규정 문장 |
| TRANSFER_PROHIBITED | 양도 금지 공연 | 공연 규정에 양도 금지 태그가 있고 판매글이 양도를 제안 | 확인 필요 | 공식 규정 문장 |
| BULK_QUANTITY | 대량 판매 | 수량 ≥ 설정값(기본 4) | 주의 | 일반 주의 (영업성은 법적 판단이므로 "의심"이라 쓰지 않음) |
| REPEATED_POST | 반복 게시 | 같은 공연의 다른 매물과 문장 유사도 ≥ 0.8 | 주의 | 비교 대상 매물 ID |
| OFF_PLATFORM_CONTACT | 외부 채널 유도 | 오픈채팅·텔레그램 등 외부 연락처 포함 | 정보 | 일반 주의 |

규칙 세부:

- 배율 기준값과 수량 기준값은 설정 파일(`rules.config.ts`)에 둔다. 코드에 숫자를 박지 않는다.
- 문장 유사도: 공백·구두점을 제거한 뒤 글자 2-gram 집합의 자카드 유사도. 외부 라이브러리 없이 구현한다. (ponytail: 매물 수가 수천 건을 넘으면 인덱싱 필요. 데모 규모에서는 전수 비교로 충분)
- 정가 이하 1회 양도는 신호 0개가 나와야 한다. 이 사례를 테스트와 발표에 반드시 포함한다.

## 6. AI 사용 설계

- 호출 위치: 서버만. 클라이언트에 API 키를 두지 않는다.
- SDK: `@anthropic-ai/sdk` (TypeScript). 원시 HTTP 호출 금지.
- 모델: `claude-opus-5-5` (기본). 비용을 줄이려면 팀 결정으로 `claude-haiku-5-5`로 바꿀 수 있도록 모델 ID를 환경 변수(`ANTHROPIC_MODEL`)로 둔다.
- 추출 호출: `output_config.format`(구조화 출력)으로 아래 스키마에 맞는 JSON만 받는다. 어시스턴트 프리필은 쓰지 않는다(현행 모델에서 400 오류).
- 캡처 입력: 같은 호출에 `image` 콘텐츠 블록(base64)을 앞에 두고 텍스트 지시를 뒤에 둔다.
- 설명 생성 호출: 규칙 엔진 결과 + 공식 문장을 입력으로 주고, "쉬운 말 2문장 이내, 법적 확정 표현 금지"로 지시한다. 설명은 신호의 의미를 바꾸지 못한다(표시용 문장만).
- 실패 처리: API 오류·타임아웃 시 추출 폼을 빈 상태로 열어 팬이 직접 입력할 수 있게 한다. `stop_reason`이 `refusal`이면 같은 처리. 서비스가 AI 없이도 끝까지 동작해야 한다.
- 비용 상한: 요청당 `max_tokens` 2048, 이미지 1장. 동일 입력 재호출 방지를 위해 입력 해시로 24시간 캐시(SQLite 테이블).

추출 스키마 (Zod로 정의, 서버 검증에도 재사용):

```ts
{
  price: number | null,            // 원 단위 정수
  seatLabel: string | null,        // 원문 표현 그대로
  quantity: number | null,
  deliveryMethod: "onsite_pickup" | "screenshot_qr" | "account_transfer" | "mobile_transfer" | "other" | null,
  prepaymentRequested: boolean,
  contactChannel: string | null,
  quotes: { field: string, text: string }[]   // 각 값의 원문 근거
}
```

## 7. 데이터 모델 (SQLite)

```
events         id, name, startsAt, venue, organizer, createdAt
price_tiers    id, eventId, tierName, facePrice
rules          id, eventId, type(본인확인필수|양도금지|캡처입장불가|현장수령필수|기타), text, sourceUrl, checkedAt
listings       id, eventId, rawText, imagePath(nullable), extracted(JSON), signals(JSON),
               priceRatio(nullable), reviewStatus(pending|reviewed|cleared), createdAt
ai_cache       inputHash, response(JSON), createdAt
```

- 이미지는 서버 로컬 `uploads/`에 저장하고 외부에 공개하지 않는다. 개인정보(전화번호·계좌번호)가 캡처에 들어올 수 있으므로 저장 전 추출 단계에서 LLM에게 "전화번호·계좌번호는 `[삭제]`로 치환"하도록 지시하고, 원문 텍스트에도 정규식으로 한 번 더 마스킹한다.
- 샘플 데이터: 공연 2건(콘서트 1, 스포츠 1), 매물 40건 안팎. 구성 비율: 정상 양도(정가 이하 1회) 25%, 웃돈만 25%, 선입금 15%, 규정 충돌 20%, 반복 게시 15%. 모두 팀이 직접 작성한 가상 글이며 실제 인물·계정을 쓰지 않는다.

## 8. API

| 메서드 | 경로 | 역할 |
|---|---|---|
| GET | /api/events | 공연 목록 |
| POST | /api/events | 공연 + 정가표 + 규정 등록 |
| POST | /api/extract | 텍스트·이미지 → 추출 JSON (AI) |
| POST | /api/listings | 수정된 추출 결과 저장 + 규칙 판정 + 설명 생성 → 신호 포함 매물 반환 |
| GET | /api/events/:id/listings | 대시보드용 매물 목록 + 반복 게시 묶음 + 분포 |
| PATCH | /api/listings/:id/review | 검토 상태 변경 |

- 모든 입력은 Zod로 검증한다. 실패 시 400과 사람이 읽을 수 있는 메시지.
- 응답 형식은 `{ ok: boolean, data, error }` 하나로 통일한다.
- 간단한 속도 제한(IP당 분당 10회 추출 호출)을 둔다. 데모 중 키 소진 방지.
- 담당자 화면·공연 등록은 환경 변수로 정한 단일 비밀번호(HTTP Basic)로 막는다. 실제 로그인·권한 체계는 범위 밖이며 발표에서 "확장 시 RBAC"로만 언급한다.

## 9. 기술 구성

| 영역 | 선택 | 이유 |
|---|---|---|
| 화면 | React + Vite + TypeScript + Tailwind | 팀이 이미 씀 |
| 차트 | Recharts | 히스토그램 1개, 가벼움 |
| 서버 | Node 20 + Express + Zod | 팀이 이미 씀 |
| DB | SQLite (`better-sqlite3`) | 파일 하나, 설치 없음 |
| AI | `@anthropic-ai/sdk` | 공식 SDK |
| 테스트 | Vitest (규칙 엔진·유사도·마스킹), Playwright 1개 시나리오(팬 입력 → 대시보드 반영) | |
| 배포 | Docker 단일 이미지 (서버가 빌드된 화면을 정적으로 서빙) | 발표장 노트북에서도 실행 |

제외: Supabase, Expo, Realtime, 로그인 체계, 외부 수집기. 2~3명이 2~4주에 관리할 부품을 줄인다.

폴더 구조:

```
ticket-radar/
  client/            React 앱
  server/
    src/
      routes/        events, extract, listings
      rules/         engine.ts, similarity.ts, rules.config.ts
      ai/            extract.ts, explain.ts, schema.ts
      db/            schema.sql, seed/
      lib/           mask.ts (개인정보 마스킹), response.ts
  docs/
  Dockerfile
```

## 10. 테스트

- 규칙 엔진: 신호 8종 각각 발생/미발생 사례, 정가 이하 1회 양도는 신호 0개, 기준값 변경 반영.
- 유사도: 같은 글 1.0, 전혀 다른 글 0.2 이하, 띄어쓰기만 다른 글 0.9 이상.
- 마스킹: 휴대폰 번호·계좌번호 형식 치환.
- API: Zod 검증 실패 400, 정상 흐름 201.
- E2E 1개: 샘플 글 입력 → 신호 카드 표시 → 대시보드 목록에 등장.
- 목표 커버리지: 서버 `rules/`, `lib/` 80% 이상.

## 11. 일정 (3주 기준, 역할 2~3명)

| 주 | 데이터·규칙 담당 | 화면 담당 | AI·발표 담당 |
|---|---|---|---|
| 1 | 공연 2건 규정·정가 입력, 샘플 매물 40건 작성, 규칙 엔진 + 테스트 | 프로젝트 뼈대, 검사 화면 입력·추출 폼 | 추출 프롬프트·스키마, 캐시, 설명 생성 |
| 2 | API 연결, 반복 게시 묶음, seed 스크립트 | 신호 카드, 대시보드 차트·표, 반응형 | 이미지 입력, 실패 처리, Docker |
| 3 | 검증표(잡은 사례·안 잡은 사례) | 다듬기, E2E | 발표 자료, 시연 대본, 배포 점검 |

2명일 때는 AI·발표를 둘이 나눈다.

## 12. 발표 시연 대본 (5분)

1. 문제: 실제 사례 수치(20만 원 티켓이 500만 원) + 개정 공연법 요지 30초.
2. 팬 화면: 선입금 + QR 캡처 판매글 붙여넣기 → 추출 → 카드 3장(정가 2.5배, 선입금, 현장 수령 규정 충돌) → 출처·확인 시각 강조.
3. 반례: 정가 이하 1회 양도 글 입력 → 신호 0개. "법이 허용하는 양도는 막지 않는다."
4. 담당자 화면: 배율 분포, 반복 게시 묶음, 검토 상태 변경.
5. 한계와 확장: 예매처 연동·실명 대조·플랫폼 API는 확장안. 진위 인증·입장 보장은 하지 않음.
