# 티켓레이더(가칭) 기획서 초안

- 작성일: 2026-10-27
- 기준 문서: 2026 AID AI-Thon 참가신청서(팀 월32) 한 장. 그 밖의 옛 설계 문서는 쓰지 않았다.
- 양식: 프로젝트관리지원기술 4주차 "팀별 기획서 작성" 표 순서 그대로
- 상태: **AI 초안, 팀 검토 전**
- 기획서의 A(최종 책임자): 팀장
- 읽는 사람: 팀 내부용. 심사위원이 볼 수 있음

표시 약속
- `[팀 결정 필요]` : AI가 대신 정하면 안 되는 칸. 팀이 채운다.
- `[가안]` : 팀이 바꿔도 되는 임시 값. 바꾸지 않으면 그대로 확정된다.
- `[출처 확인됨]` : 2026-10-27에 기사 본문을 직접 열어 문장을 확인한 숫자.
- `[출처 확인 후 채울 칸]` : 제목만 봤거나 본문을 확인하지 못한 숫자. 확인 전에는 발표에 쓰지 않는다.

## 2. 목표 (발표 때 예/아니오로 판정할 숫자)

해커톤이라 "가입자 수" 같은 사용자 숫자는 잴 수 없다. 그래서 이 프로젝트의 목표는 **동작을 증명하는 숫자**로 잡는다. 아래 3개는 `[가안]`이며, 숫자(10건, 8건, 2건)는 팀이 바꿀 수 있다.

| 번호 | 발표 때 달성할 숫자 | 어떻게 재는가 | 증명하는 것 |
|---|---|---|---|
| 1 | 팀이 직접 쓴 **가상 판매글 10건** 중 **8건 이상**에서, 미리 적어 둔 "나와야 할 확인사항"과 같은 결과가 나온다 `[가안]` | 글마다 기대 결과를 표로 적어 두고(검증표), 발표 전 실제 결과와 한 줄씩 비교 | 맞게 잡는다 |
| 2 | 정가 이하로 1장만 파는 **정상 양도 글 2건**에서 확인사항이 **0건**이다 `[가안]` | 시연에서 그 글 2건을 직접 넣어 결과 화면을 보인다 | 멀쩡한 글을 의심하지 않는다 |
| 3 | **AI 호출을 끈 상태**에서도 "입력 → 직접 입력 → 대조 → 표시"가 **끝까지 1회 완주**된다 `[가안]` | AI 키를 뺀 채로 시연 흐름을 한 번 실행 | AI가 실패해도 서비스는 끝까지 간다 |

> 목표 1·2의 "가상 판매글"은 팀이 직접 쓴 글이어야 한다. 실제 사람의 글·연락처·계정을 쓰지 않는다.

## 3. 해결 방향과 선택

신청서에서 이미 정해진 것과, 팀이 새로 정해야 하는 것을 나눴다. 선택지마다 장단점을 적었고 **"우리 팀의 선택" 칸은 비워 두었다.** 이유를 말하지 못하는 선택은 선택이 아니라 우연이므로, 고른 뒤 "왜"와 "버린 선택지"를 꼭 채운다.

### 3.1 신청서에서 이미 정해진 방향 (팀 확인만)

| 선택 지점 | 신청서의 내용 | 뜻 |
|---|---|---|
| 해커톤 시연 범위 | 공연 1건, "판매글 입력 → AI 정보 추출 → 공식 근거 대조 → 확인사항 표시" | 공연 여러 건, 주최 측 등록 화면은 이번 범위가 아님 |
| AI가 할 일 / 서비스(코드)가 할 일 | AI는 가격·좌석·전달 방식 등 핵심 정보를 **추출**, 사용자가 **확인·수정**, 서비스가 공식 가격·규정과 **대조** | 판단(대조)은 AI가 아니라 코드가 한다. 같은 글을 넣으면 항상 같은 결과가 나와야 하고, 왜 그렇게 나왔는지 설명할 수 있어야 하기 때문 |
| 결과를 부르는 이름 | "확인이 필요한 부분"을 원문과 공식 출처와 함께 표시. **티켓 진위나 사기·불법 여부를 자동으로 확정하지 않는다** | 화면과 발표 어디에도 "암표", "불법", "사기"라고 단정하는 문구를 쓰지 않는다 |

### 3.2 팀이 정해야 하는 선택 지점

2026-10-27 팀원 1명의 답변을 반영했다. 같은 날 자동 수집과 광고·구독은 해커톤 범위 밖 "확장"으로 옮기고, 플랫폼은 반응형 웹 한 벌로 정했다. **A(팀장) 승인 전.**

| 선택 지점 | 선택지와 장단점 | 우리 팀의 선택 | 왜 그렇게 정했나 | 버린 선택지 |
|---|---|---|---|---|
| **플랫폼** | ① 웹(PC+모바일 브라우저): 설치 없이 링크로 시연, 팀이 익숙한 기술로 빠름 / ② 모바일 앱: 팬이 실제로 쓰는 환경에 가깝지만 심사 기기마다 설치 필요, 해커톤 기간에 부담 / ③ 둘 다: 범위 2배 | ① 웹, **반응형 화면 한 벌** | PC와 모바일을 모두 브라우저로 쓰게 한다. 설치 없이 링크로 시연할 수 있다. 화면은 한 벌만 만들고 화면 폭에 따라 배치가 자동으로 바뀌게(반응형) 한다 | ② 앱, ③ 웹+앱, 그리고 "PC용·모바일용 화면을 따로 두 벌" (처음 의견이었으나 Must 화면 작업이 두 배가 되어 버림) |
| **판매글 입력 방식** | ① 텍스트 붙여넣기만: 가장 단순, AI 추출 정확도 측정이 쉬움 / ② 캡처 이미지도 받기: 실제 팬의 행동(캡처)에 가깝지만 이미지 읽기 오류가 하나 더 생김 / ③ 둘 다: ①을 끝낸 뒤 시간이 남으면 | ② 텍스트 + 캡처 이미지 | 글 복사가 막힌 사이트가 분명히 있어, 캡처도 받아야 팬이 편하다 | ① 텍스트만, ③ 나중에 캡처. 메모 `[가안]`: 캡처는 AI가 이미지를 잘못 읽는 경우가 더해지므로 목표 1 검증표(10건)에 캡처 글을 2건 이상 넣는다. 일정이 밀리면 Must에서 가장 먼저 빼는 후보 |
| **공식 정가·규정 데이터를 넣는 방법** | ① 팀이 공연 1건의 공식 공지를 손으로 옮겨 적어 파일로 넣음(출처 URL·확인 날짜 함께): 가장 단순 / ② 관리자 입력 화면: 화면 하나가 더 필요 / ③ 예매처·공지 자동 수집: 이용약관·법 위험, 해커톤에 부적합 | ① 손 입력 + ②의 관리자 재확인 화면 | 신청서 범위가 "공연 1건"이라 공지 1건을 손으로 옮겨 적는 편이(출처 URL·확인 날짜 함께) 수집기를 만드는 것보다 훨씬 작다. 예매처 약관의 자동 수집 금지 위험도 피한다. 사람이 관리자 화면에서 값을 재확인·수정할 수 있게 둔다 | ③ 자동 수집 (처음 의견. 사이트마다 구조 분석이 필요하고 구조가 바뀌면 깨지며, 봇 차단·약관 문제가 있어 **확장**으로 옮김. 발표에서 "공연이 늘면 자동 수집으로 확장" 한 줄만 말한다) |
| **로그인** | ① 없음: 팬이 바로 씀, 시연 단순 / ② 팬 로그인: 제보 누적(Should)에 유리하지만 회원가입·비밀번호 저장 책임이 생김 / ③ 담당자 화면만 비밀번호: Should 범위가 들어올 때만 필요 | ① 없음 | 팬이 로그인 없이 바로 쓴다. 회원가입·비밀번호 저장 책임이 없어 시연이 단순하다 | ② 팬 로그인, ③ 담당자 비밀번호. **확장 아이디어(이번 범위 밖)**: 비로그인은 광고 노출, 회원가입 후 구독 결제하면 광고 없이 이용. 결제는 결제대행 계약·개인정보·보안 책임이 따라오고 해커톤 시연 흐름과 무관해 4절 Won't에 명시. 발표에서 "참고용 서비스에 광고가 붙으면 중립성은?" 질문이 나올 수 있으니 확장으로만 언급 |
| **AI 추출이 실패했을 때** | ① 빈 입력칸을 열어 팬이 직접 입력(목표 3과 연결) / ② 오류 안내만 하고 중단 | ① 직접 입력 | AI가 안 되더라도 사람이 직접 입력해 결과 화면까지 갈 수 있어야 한다 (목표 3과 일치) | ② 중단 |
| **제보 누적(Should)을 어디에 저장** | ① 파일 하나 또는 가벼운 DB 1개 / ② 외부 클라우드 DB: 계정·비용·배포가 늘어남 | ① 서버 안 파일 또는 가벼운 DB 1개 | 지금은 시연용이라 실제 서비스가 아니므로 충분하다 | ② 외부 클라우드 DB |

> 6주차(아키텍처)에서 다시 다룰 "바꾸기 비싼 결정"은 이 중 **데이터 저장 위치, 로그인, 배포 위치**다. 기획서에서는 방향만 정하고, 이유는 6주차 결정 기록(ADR)에 남긴다.

## 4. 범위

| 해커톤 발표까지 (Must) | 시간이 남으면 (Should) | 이번에는 안 함 (Won't) | 안 하는 이유 |
|---|---|---|---|
| 공연 1건 선택 | 팬들의 제보가 쌓이면 같은 판매자 혹은 같은 연락처로 반복 올린 글 찾아 보여주기 (신청서 To-Be) | 티켓 진위·사기·불법 여부 자동 확정 (신청서에 명시) | 법적 판단은 신고기관이 한다. 서비스가 단정하면 멀쩡한 판매자에게 피해를 줄 수 있다 |
| 판매글 텍스트 입력 | 제보를 원하는 팬에게 관련 근거 정리 + 공식 신고 경로 안내 (신청서 To-Be) | 판매자 신원(이름·아이디·연락처) 공개 `[가안]` | 사적 제재가 되고 개인정보 문제가 생긴다 |
| AI가 가격·좌석·전달 방식 등 핵심 정보 추출 | | 신고 대행(서비스가 대신 제출) `[가안]` | 제출은 팬이 공식 신고센터에 직접 한다. 서비스는 자료만 정리 |
| 추출 결과를 팬이 확인·수정 | | 외부 사이트(중고 거래 앱 등) 자동 수집 `[가안]` | 이용약관·법 위험. 팬이 붙여넣은 글만 다룬다 |
| 공식 정가·입장·양도 규정과 대조 | | 공연 여러 건, 주최 측 공연 등록 화면 `[가안]` | 신청서 범위가 공연 1건. 데이터는 팀이 손으로 넣는다 |
| 확인이 필요한 문구를 원문 + 공식 출처와 함께 표시 | | 결제·거래 중개, 티켓 양도 기능 `[가안]` | 우리는 "확인"만 돕는다. 거래에 끼면 책임 범위가 완전히 달라진다 |
| AI 실패 시 직접 입력으로 끝까지 진행 (목표 3) | | 결제·구독·광고 (수익 모델) | 해커톤 시연 범위 밖. 결제는 결제대행 계약·보안 책임이 따라온다. 아이디어는 3.2절 로그인 행에 "확장"으로 기록 |
| 판매글 캡처 이미지 입력 (3.2절 선택 2) | | 공식 공지 자동 수집 | 공연 1건이라 손 입력이 훨씬 작고, 예매처 약관·봇 차단 위험이 있다. "확장"으로만 언급 |
| 관리자가 공식 정가·규정을 재확인·수정하는 화면 (3.2절 선택 3) | | 회원가입·로그인 | 3.2절 로그인 선택 ①. 시연에 필요 없고 비밀번호 저장 책임이 생긴다 |

**확장 아이디어 (이번 범위 밖, 발표 마지막 장에 한 줄씩)**: 공연이 늘면 공식 공지 자동 수집 / 수익 모델(비로그인 광고, 구독 결제 시 광고 제거) / 공연 여러 건·주최 측 등록 화면.

> Won't는 5개 이상이어야 한다. `[가안]` 표시된 5개는 AI가 신청서 문장에서 유추한 후보이므로 팀이 빼거나 바꾼다. 표시 없는 3개(결제·구독·광고, 자동 수집, 회원가입·로그인)는 2026-10-27 팀원 답변으로 정한 것이다. **확정된 Won't 목록은 5주차 화면 명세표의 "절대 넣지 않는 것" 칸으로 그대로 내려간다.**

## 5. 화면 흐름 (핵심 목적 하나)

| 항목 | 내용 |
|---|---|
| **이 흐름의 목적** | 팬이 중고 판매글 하나를 결제 전에 공식 안내와 비교해 "확인이 필요한 부분"을 안다 |

| 순서 | 화면 | 사용자가 하는 일 | 다음 화면으로 가는 조건 |
|---|---|---|---|
| 1 | 판매글 입력 | 공연을 고르고 판매글을 붙여넣거나 캡처 이미지를 올린다 | 공연이 선택되어 있고 글 또는 이미지 중 하나 이상 있음 |
| 2 | 추출 결과 확인 | AI가 뽑은 가격·좌석·전달 방식을 보고 틀린 값을 고친다. AI가 실패했으면 빈 칸에 직접 쓴다 | 가격 또는 전달 방식 중 하나 이상 입력됨 |
| 3 | 확인사항 결과 | 항목마다 판매글 원문 구절 ↔ 공식 안내 문장 ↔ 출처를 나란히 본다. 확인사항이 없으면 "찾지 못했다"는 안내를 본다(안전하다고 말하지 않음) | 목적 달성 |
| 4 (Should) | 제보 근거 정리 | 위 결과를 한 장으로 정리해 두고 공식 신고센터 링크를 본다 | 팬이 "제보 자료 만들기"를 눌렀을 때만 |

> 첫 화면이 로그인이 아니라 입력 화면이다(5주차 흔한 실수 피하기). 화면마다 입력칸은 3개 이하를 목표로 한다. 이 표는 5주차 화면 명세표의 입력이 된다.

## 6. 일정과 역할

### 6.1 일정 (단계 순서)

팀 결정에 따라 **마감일·발표일·개발 가능 시간은 이 기획서에서 고려하지 않는다.** 그래서 주차 대신 "끝나 있어야 하는 것"의 순서로 적는다. 날짜가 정해지면 발표일에서 거꾸로 이 표에 날짜를 붙인다.

| 단계 | 이 단계가 끝날 때 되어 있어야 하는 것 | A (책임자) `[가안]` |
|---|---|---|
| 1 | 이 기획서의 `[팀 결정 필요]` 칸이 모두 채워지고 A가 승인 | 팀장 |
| 2 | 화면 명세표(화면 4개, 빈·로딩·오류·정상 상태 포함)와 구성도·데이터 목록·API 목록 1장 | 화면 담당(화면), 서버 담당(구조) |
| 3 | 공연 1건의 공식 정가·규정이 출처·확인 날짜와 함께 파일로 들어가 있음. 가상 판매글 10건 + 정상 양도 글 2건과 각각의 기대 결과(검증표) 작성 | 서버 담당 |
| 4 | 판매글 입력 → AI 추출 → 직접 수정 → 대조 → 표시가 화면에서 끝까지 동작 (Must 완료) | 화면 담당 |
| 5 | 목표 1·2·3을 실제로 재서 결과를 기록. 전원이 함께 시험하고 "구현한 것 / 못 한 것" 구분 (신청서 팀 규칙 4) | 테스트 담당 |
| 6 | (시간이 남으면) Should 2개 중 하나 이상 | 테스트 담당 |
| 7 | 발표 자료, 시연 대본, 리허설 2회 | 팀장 |

### 6.2 역할 (RACI)

R = 실제로 하는 사람, A = 승인·최종 책임(항목마다 딱 1명), C = 미리 의견을 묻는 사람, I = 결과를 알려 줄 사람. 신청서의 역할 4개를 기준으로 했고 A 배치는 `[가안]`이다.

| 항목 | 팀장 | 화면 담당 | 서버 담당 | 테스트 담당 |
|---|---|---|---|---|
| 기획서·범위·일정 | **R/A** | C | C | C |
| 팬용 화면, 판매글 입력·결과 확인 흐름 | C | **R/A** | I | I |
| 공식 공연 정보·규정 데이터, 분석(추출·대조) API | I | C | **R/A** | I |
| 제보·담당자 화면 (Should) | I | C | I | **R/A** |
| 통합 테스트, 목표 숫자 측정, 검증표 결과 | I | C | C | **R/A** |
| 발표 자료·시연 대본 | **R/A** | C | C | C |
| AI가 만든 코드·자료의 최종 검사 | **A** | R(자기 담당) | R(자기 담당) | R(자기 담당) |

> 기획서상은 4명이지만 실제로는 2인 체제가 될 가능성이 높다. 그 경우 A는 바꾸지 않고 R만 두 사람이 나눠 맡는다(7절 위험 1 참고).

### 6.3 팀 규칙과 AI 사용 규칙 (신청서 2. 팀빌딩에서 옮김)

1. 각자 맡은 기능과 완료 일정을 정하고, 진행 상황과 어려운 점을 매일 공유한다.
2. 기획이나 기능을 변경할 때는 팀원들과 논의하고 결정 내용을 기록한다.
3. 생성형 AI로 만든 코드와 자료는 담당자가 직접 확인·수정한 뒤 결과물에 반영한다.
4. 발표 전에는 모든 팀원이 기능을 함께 시험하고, 구현한 내용과 아직 구현하지 못한 내용을 정확히 구분한다.

**완료의 정의(DoD) `[가안]`** : Must 흐름이 "완료"라고 말하려면 ① 팀원 자기 컴퓨터가 아니라 시연용 환경에서 동작 ② 정상 글, AI 실패, 빈 입력, 공식 규정에 없는 좌석 등급의 네 경우를 처리 ③ 담당자가 아닌 다른 팀원이 직접 써 보고 승인. 이 세 가지가 없으면 AI는 "내 화면에 뜬다" 수준에서 멈춘다.

## 7. 위험

위험 없는 기획서를 가장 믿지 않는다. 아래는 AI가 쓴 후보 `[가안]`이며, **가능성 칸과 대응은 팀이 직접 다시 적는다.**

| 번호 | 틀어질 수 있는 것 | 가능성 (고/중/저) | 그러면 어떻게 할 것인가 |
|---|---|---|---|
| 1 | 실제로는 2명만 개발하게 된다 | `[팀 결정 필요]` (사용자 답변 기준으로는 높음) | A는 그대로 두고 R만 둘이 나눈다. Should는 처음부터 손대지 않고, Must도 순서 4(화면 연결) 전에 범위를 한 번 더 줄인다 |
| 2 | AI가 가격·좌석·전달 방식을 틀리게 뽑는다 | | 팬이 고칠 수 있는 확인·수정 화면(흐름 2)을 Must에 둔다. 대조는 코드가 하므로 AI 오류가 결과 판정까지 번지지 않는다. 목표 1로 정확도를 숫자로 잰다 |
| 3 | 공연 1건의 공식 정가·입장 규정을 공식 문서에서 못 찾거나 문장이 애매하다 | | 공식 공지가 분명한 공연으로 바꾼다. 애매한 규정은 "확인이 필요한 부분"으로만 표시하고 단정하지 않는다 |
| 4 | "암표 판별 서비스"로 오해받아 심사에서 "그럼 틀리면 책임은?" 질문을 받는다 | | 모든 화면에 "참고용이며 최종 판단은 사용자가 한다" 고정 문구. 발표 첫 장에 "확정하지 않는다"를 신청서 문장 그대로 넣는다. 금지 단어(암표상, 불법, 사기) 검사 |
| 5 | 배경 숫자의 출처가 틀리거나 오래됐다 | | 1절 출처 표에서 `[출처 확인 후 채울 칸]`은 쓰지 않는다. 2023년 사례는 연도를 명시한다. 법 조항은 법령 원문으로 재확인 |
| 6 | 시연 당일 AI 호출이 실패하거나 인터넷이 끊긴다 | | 목표 3(AI 없이 완주)이 곧 대비책. 시연 글은 미리 한 번 넣어 두고, 녹화 영상을 백업으로 둔다 |
| 7 | 캡처 이미지를 AI가 잘못 읽어 가격·좌석이 틀리게 나온다 | | 흐름 2(확인·수정)에서 팬이 고친다. 검증표에 캡처 글을 넣어 정확도를 따로 잰다. 심하면 캡처를 Should로 내린다 |
