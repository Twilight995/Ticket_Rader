## 단계와 완료 기준

각 단계는 "완료 기준"을 사람이 직접 확인한 뒤 커밋한다. AI가 "됐다"고 말하는 것은 완료가 아니다(2주차).

### 0단계. 환경 확인 (30분)

- 할 일: `server/`에 빈 Spring Boot 프로젝트, `client/`에 빈 Vite React 프로젝트. `GET /api/health`가 `{ ok: true, data: { status: "up" }, error: null }`을 돌려주고, 로컬 MySQL에 붙는다. 루트에 `.env.example`, `.gitignore`(`.env`, `node_modules`, `target`, `dist`).
- 완료 기준: 팀 노트북에서 명령 하나(`scripts/start.ps1` 또는 README의 두 줄)로 서버가 뜨고 브라우저에서 health가 보인다. MySQL이 꺼져 있을 때 어떤 오류가 나는지 README에 적어 둔다.

### 1단계. API 계약서 (코드보다 먼저)

- 할 일: `docs/api-contract.md`에 아키텍처 STEP 4의 Must API 5개를 9주차 양식으로 한 장씩 쓴다: 공연 조회 / 판매글 추출 / 비교 / 관리자 공연 조회 / 관리자 공연 저장. 요청·응답 JSON의 칸 이름까지 정한다. 추출 응답에는 `aiStatus: "ok" | "fallback"`이 있고 연락처 칸은 없다.
- 완료 기준: 화면 담당이 이 문서만 보고 가짜 응답으로 화면을 만들 수 있다. 각 계약서의 "서버가 확인할 것"이 아키텍처 STEP 4와 같다.

### 2단계. 공연 데이터와 관리자 API

- 할 일: 엔티티 3개(공연, 정가 등급, 규정) + JPA Repository. 서버 시작 시 DB가 비어 있으면 `seed/event.json`을 넣는다. `GET /api/event`(공개), `GET /api/admin/event`·`PUT /api/admin/event`(HTTP Basic, 비밀번호는 환경 변수). 입력 검증: 출처 URL은 http(s), 정가 0 이상 정수, 등급 이름 중복 없음, 규정 종류 5개 중 하나.
- 테스트 먼저: 비밀번호 없음 → 401 / 잘못된 값 → 400 + 한국어 메시지 / 저장 후 조회하면 같은 값 / seed 두 번 실행해도 중복 없음.
- 완료 기준: 9주차 점검 ①③⑤를 실제 요청으로 통과. DB를 열어 봐도 비밀번호가 없다(④).

### 3단계. 비교 API (규칙 엔진) — 핵심

- 할 일: `POST /api/check`. 입력(가격·좌석·수량·전달 방식·선입금 여부)과 공연의 정가표·규정을 받아 **순수 함수**로 확인사항 목록을 만든다. 확인사항 종류(기획서·명세표에서): 정가보다 높음(배율 표시) / 정가 대조 불가(좌석 등급 못 맞춤, 오류 아님) / 선입금 요구 / 전달 방식이 규정과 충돌 / 양도 금지 공연 / 수량 많음. 종류당 카드 1장, 심각도 라벨 정보·주의·확인 필요. 기준값(배율 1.5, 수량 4 등)은 설정 파일에. 각 확인사항에 판매글 구절·공식 문장·출처 URL·확인 날짜·템플릿 설명.
- 테스트 먼저(수용 기준이 곧 테스트): 정가 이하 1장 정상 양도 글 2건 → 확인사항 **0건** / 시연 글(정가 1.5배 + 선입금 + QR 캡처) → 정확히 3건 / 기준값을 바꾸면 결과가 바뀜 / 같은 입력 두 번 → 완전히 같은 결과 / 금지 단어가 템플릿 문장에 없음.
- 완료 기준: 테스트 전부 통과, 규칙 엔진 파일에 숫자가 직접 쓰여 있지 않음, Controller에 판단 코드가 없음.

### 4단계. 추출 API (AI)

- 할 일: `POST /api/extract`(텍스트 또는 이미지). 순서: 입력 검증(글 5,000자 이하, 이미지는 앞부분 바이트로 PNG/JPG·5MB) → 연락처 패턴 마스킹(`[삭제]`) → Claude 공식 Java SDK로 구조화 출력(가격 1장당 정수·좌석·수량·전달 방식 5종 중 하나·선입금 여부·근거 구절) → 응답. 판매글은 구분 태그로 감싸 "분석할 자료"로만 취급(프롬프트 인젝션 대비). 실패·시간 초과(20초)·거부·형식 불일치 → `aiStatus: "fallback"` + 빈 값, HTTP 200. 같은 접속 분당 10회 제한. 이미지는 메모리에서만 쓰고 버린다.
- 테스트 먼저(SDK는 가짜로 끼움): 글도 이미지도 없음 → 400 / 확장자만 png인 텍스트 → 400 / SDK 오류 → 200 + fallback / 응답에 `contacts`·전화번호가 없음 / 마스킹이 날짜·가격·좌석(`150,000원`, `2026-12-20`, `A구역 12열`)은 지우지 않음.
- 완료 기준: 실제 키로 가상 글 3건을 넣어 추출이 되고, 키를 빼면 fallback으로 흐름이 이어진다. 로그에 원문·키가 없다.

### 5단계. 화면 ⓪①②③ + ⑤

- 할 일: 홈(⓪)부터 시작해 명세표의 네 가지 상태를 화면마다 전부 만든다. 홈은 공연 조회 API 결과로 공연 카드를 채우고, 공연이 없으면 빈 상태(안내 + 버튼 비활성). 디자인 토큰을 CSS 변수(`--tr-bg` 등)로 옮기고 값을 컴포넌트에 직접 쓰지 않는다. 부품(버튼·입력칸·안내·카드·배지)을 먼저 만들고 화면을 조립한다. 심각도는 색 + 글자 라벨. 버튼 글씨는 명세표 문구 그대로("이 판매글 확인하기", "공식 안내와 비교하기", "수정 내용 저장"). 데이터 가져오기·보내기는 커스텀 훅으로 분리.
- 완료 기준: 390px에서 가로 스크롤 없음, 1024px에서 PC 배치. AI 키를 뺀 상태로 ① → ② 직접 입력 → ③ 결과까지 완주(수용 기준 3). 화면 문구에 금지 단어 없음(자동 검사 테스트 1개).

### 6단계. 검증표와 수용 기준 측정

- 할 일: 가상 판매글 10건(캡처 2건 포함)과 각 글의 기대 확인사항을 `docs/validation.md` 표로 적고, 실제 결과를 옆에 기록. 정상 양도 글 2건 결과, AI 없이 완주 여부도 같은 표에.
- 완료 기준: 10건 중 8건 이상 일치, 정상 글 0건, AI 없이 완주. 담당자가 아닌 팀원이 직접 돌려 보고 승인(완료의 정의 ③).

### 7단계 (Must 끝난 뒤). Should

- 검사 기록 저장(ADR 2 확장: 마스킹된 원문 + 연락처 해시만) → 같은 연락처 반복 표시 → ④ 제보 근거 한 장(인쇄용). 저장 코드를 처음부터 분리해 두었다면 여기서 Service에 저장 호출 한 줄과 Repository 하나가 추가될 뿐이다.

## 첫 세션의 범위

첫 세션은 **0·1·2단계와 3단계의 테스트까지**. 3단계 구현이 되면 그 자리에서 커밋하고 끝낸다. 4단계(AI)는 키와 비용이 걸리므로 다음 세션에서 사용자와 함께 시작한다.

## 세션이 끝날 때 남길 것

- 커밋(단계마다), `README.md`에 실행 두 줄과 `.env` 칸 설명, 다음 세션이 이어서 할 단계와 막힌 점을 `docs/dev-log.md`에 날짜와 함께 한 줄씩.
