# 검증표 (6단계, 수용 기준 측정)

수용 기준(`prd-ticket-radar-for-ai.md` 수용 기준 1~3)을 재는 표다. 글 10건은 **전부 팀이 지어낸 가상 글**이다. 실제 사람·실제 글이 아니고, 연락처는 `010-0000-xxxx` 대역과 가짜 계좌·아이디만 썼다.

## 기준

- 공연: seed 가상 공연(`server/src/main/resources/seed/event.json`). 정가 VIP 165,000 / R 143,000 / S 121,000원. 규정: 현장 수령 필수, 캡처 입장 불가, 본인 확인 필수.
- 규칙 엔진 기준값(`application.properties`): 정가 대비 1.5배 이상이면 "확인 필요", 그 아래로 정가 초과면 "주의"(`price-check-ratio=1.5`). 4장 이상이면 "수량 많음"(`quantity-high-threshold=4`).
- 전달 방식과 규정 짝: 캡처·QR ↔ 캡처 입장 불가, 계정 양도 ↔ 본인 확인 필수, 모바일 티켓 전송 ↔ 현장 수령 필수. 현장 수령·기타는 충돌 없음.
- **일치**의 뜻: AI 추출 → 비교까지 거친 실제 확인사항(종류 + 심각도, 순서까지)이 기대 확인사항과 같다.
- 데이터 원본은 `docs/validation/cases.json` 하나다. 이 표, 서버 테스트 `ValidationCasesTest`, 스크립트 `scripts/validate.ps1`이 같은 파일을 읽는다. 글을 고치면 그 파일을 고친다.

기대 추출값 순서: **1장당 가격 / 좌석 / 수량 / 전달 방식 / 선입금**. `-`는 글에 없음(null).

남은 일: AI 할당량이 돌아오면 아래 명령으로 "실제 추출값"과 "일치 여부"를 채운다. 그리고 담당자가 아닌 팀원이 직접 돌려 보고 승인한다(완료의 정의 ③).

## 실제 결과를 채우는 방법

1. 서버를 실제 AI 설정으로 띄운다. `.env`에 `AI_PROVIDER=gemini`, `AI_MODEL`, `GEMINI_API_KEY`가 있어야 한다.

```bash
powershell -ExecutionPolicy Bypass -File scripts/start.ps1
```

2. 다른 터미널에서 검증 스크립트를 돌린다. 글 10건(9·10번은 이미지 파일)을 `POST /api/extract`로 보내고, 읽은 값으로 `POST /api/check`를 불러 기대 확인사항과 비교한다. 무료 티어 한도 때문에 글 사이에 5초 쉰다(약 1분).

```bash
pwsh -File scripts/validate.ps1
```

3. 찍힌 줄(`| 번호 | 실제 추출값 (ok/fallback) | 실제 확인사항 | 일치 |`)을 위 표의 "실제 추출값"·"일치 여부" 칸에 옮기고, 마지막 줄 "일치 N / 10"을 결과 표에 적는다. 실제 확인사항 칸은 AI가 읽은 값 기준으로 바꿔 적는다.

주의:
- 스크립트는 PowerShell 7(`pwsh`)이 필요하다(`powershell` 5.1에는 `-Form`이 없다).
- 기대값은 seed 정가·규정 기준이다. ⑤ 관리자 화면에서 정가를 바꿔 둔 서버에 돌리면 결과가 달라진다(예: VIP를 170,000원으로 바꾸면 4번 가격 카드가 "주의"로 내려감). 서버를 새로 띄우거나 seed 값으로 되돌린 뒤 돌린다.
- 같은 접속은 분당 10회까지라 1분 안에 다시 돌리면 429가 날 수 있다. 실패한 글은 "추출 요청 실패(429)"처럼 상태 코드와 함께 찍히고 나머지 글은 계속 진행한다.
- 7번(종이 티켓 택배)은 규정 "현장 수령 필수"와 어긋나 보이지만, 규칙 엔진은 전달 방식 "기타"에 짝지은 규정이 없어 충돌 카드를 만들지 않는다. 기대값은 엔진 기준이다. 택배를 "현장 수령 필수"와 짝지을지는 팀이 정할 일이다.

AI 없이 규칙 엔진만 다시 확인하려면 `pwsh -File scripts/validate.ps1 -SkipAi` (서버만 떠 있으면 된다), 또는 `server`에서 `.\mvnw.cmd test -Dtest=ValidationCasesTest`.
