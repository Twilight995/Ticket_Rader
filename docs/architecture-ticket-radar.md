# 티켓레이더(가칭) 시스템 아키텍처 (6주차)

- 작성일: 2026-10-28
- 입력 문서: `docs/prd-ticket-radar.md`(범위·비기능 요구), `docs/screen-spec-ticket-radar.md`(보여줄 정보 → 데이터, 행동 → API), `docs/ticket_rader_mock.pen`
- 양식: 프로젝트관리지원기술 6주차 3부 STEP 1~5 그대로
- 아키텍처의 A: 서버 담당 (기획서 RACI "공식 공연 정보·규정 데이터, 분석 API" R/A). 최종 승인은 팀장.
- 이 문서는 다음 단계부터 AI에게 주는 **지도**다. AI가 만든 코드가 이 구조에서 벗어나면 코드가 아니라 이 문서를 먼저 고친다.
- AI가 추론해 채운 칸은 **부록**에 모았다. `[팀 확인]` 1곳(팀이 할 줄 아는 기술)은 팀만 답할 수 있다.

## 0. 구조를 정하는 비기능 요구사항 (기획서에서 옮김)

기능은 구조를 정하지 않는다. 구조를 정하는 건 아래 조건들이다.

| 비기능 요구사항 | 어디서 왔나 | 구조에 미치는 영향 |
|---|---|---|
| 해커톤 시연. 동시 사용자는 심사위원·팀원 수준(10명 이하) | 기획서 2절 목표 | 서버 1대, DB 파일 1개면 충분. 대기열·캐시 서버·서버 분리 전부 불필요 |
| AI가 실패해도 끝까지 동작 (목표 3) | 기획서 2절 | AI 호출은 "있으면 좋은 부품"으로 떼어 둔다. 판정은 코드가 한다 |
| 공연 1건, 데이터는 손으로 넣은 파일 | 기획서 3.2절 | 공연 등록 화면·자동 수집기 없음. 파일 하나를 서버가 읽고, 관리자 화면에서 고쳐 쓴다 |
| 로그인 없음, 서버 안 저장 | 기획서 3.2절 | 회원 테이블·세션·외부 인증 서비스 없음. 외부 클라우드 DB 없음 |
| 캡처 이미지 PNG/JPG 5MB 이하 | 화면 명세표 ① | 이미지를 저장할지 말지가 갈림 (STEP 1 "사진 저장") |
| 연락처 원문을 보관하지 않음, 실제 사람 글 사용 금지 | 기획서 4절 Won't | 저장하는 데이터 자체를 최소로. Should(제보 누적)에서만 해시 저장 |
| 발표 당일 안 돌아가는 것이 최대 위험 | 기획서 7절 위험 6 | 배포는 "팀 노트북에서 한 명령으로 실행"이 기본. 인터넷이 끊겨도 AI만 빠지고 나머지는 동작 |

## STEP 1. 선택 지점 결정

| 항목 | 내용 |
|---|---|
| **팀명** | 월32 |
| **아키텍처의 A** | 서버 담당 |

| 선택 지점 | 우리 팀의 선택 | 이유 (팀에 할 줄 아는 사람, 비기능 요구사항, 배포) | 버린 선택지 |
|---|---|---|---|
| **클라이언트 기술** | 웹, 반응형 한 벌. **구체 기술은 `[팀 확인]`**: 팀 전원이 이미 써 본 것 하나로 통일 (가안: React + Vite) | 기획서에서 웹으로 확정. 6주차 기준은 "팀에 이미 할 줄 아는 사람이 있는가"뿐이다. 가안 React는 자료가 가장 많고 AI가 가장 안정적으로 코드를 내놓는다는 이유이지, 팀이 Vue나 순수 HTML을 더 잘 알면 그쪽이 맞다 | 모바일 앱(기획서에서 버림), 팀원마다 다른 기술로 시작 |
| **서버 기술** | **`[팀 확인]`**: 1학기에 배운 서버 기술을 쓰지 않을 이유가 없으면 그것 (수업 기준 Spring Boot). 팀 전원이 Node.js를 더 잘 쓰면 Node.js | 6주차 기준 "1학기에 배운 걸 쓰지 않을 이유가 있는가". AI 호출용 공식 SDK는 Java·Node 둘 다 있어 어느 쪽이든 막히지 않는다 | Python(팀이 쓰지 않는다면), 서버 없이 브라우저에서 AI 직접 호출(API 키가 노출되므로 금지) |
| **데이터베이스** | SQLite 파일 1개 (서버와 같은 컴퓨터) | 데이터가 표 모양이고(공연·정가·규정·검사 결과) 양이 수백 건을 넘지 않는다. 설치·계정·네트워크 없이 파일 하나라 발표 노트북에서 가장 안 깨진다. 7주차 수업이 MySQL 기준이면 그때 바꿔도 코드 변경이 작다(저장 코드를 한 곳에 모아 둠, ADR 2) | MySQL/PostgreSQL(설치·운영 부담, 지금 규모에 불필요), MongoDB(표 모양 데이터에 맞지 않음), 외부 클라우드 DB(기획서에서 버림) |
| **사진(캡처 이미지) 저장** | **저장하지 않는다.** 올린 이미지는 서버 메모리에서 AI에 보내고 응답을 받으면 버린다 | Must에서 이미지는 "글자를 뽑는 재료"일 뿐 다시 볼 일이 없다. 저장하지 않으면 개인정보(캡처 속 연락처·계정)가 남지 않고, 디스크·외부 저장소 결정 자체가 사라진다 | 서버 디스크(발표 노트북이면 살아 있지만 지울 책임이 생김), 외부 저장소(계정·비용·설정) |
| **인증** | 팬: 없음. 관리자 화면: 환경 변수에 둔 비밀번호 1개로 브라우저 기본 로그인창(HTTP Basic) | 기획서 "로그인 없음, 회원가입 Won't"는 팬 기준이다. 관리자 화면은 데이터를 **고치는** 화면이라 "주소만 아는 사람"으로 두면 서버가 확인할 것이 없어진다(6주차 "클라이언트는 믿지 않는다"). 회원 테이블 없이 비밀번호 하나면 충분 | 직접 회원 구현(Won't), 외부 인증 서비스(계정·설정이 늘고 시연에 불필요), 관리자 화면 무인증(화면 명세표 초안의 "주소 아는 사람만" → 이 문서에서 바꿈) |
| **배포 위치** | 발표용 팀 노트북 1대에서 서버 1개 실행 (화면 파일도 같은 서버가 제공). 외부 접속이 꼭 필요해지면 그때 무료 호스팅 1곳을 추가 | 비기능 "발표 당일 안 돌아가는 것이 최대 위험". 노트북 로컬이면 인터넷이 끊겨도 AI만 빠지고 나머지는 동작(목표 3). 심사 기기에서 봐야 하면 같은 와이파이의 노트북 주소로 접속 | 클라우드 무료 티어를 처음부터(무료 티어는 첫 접속이 느리거나 잠들어 있어 시연 중 멈출 수 있음. 필요해지면 ADR 3대로 추가), 학교 서버(권한·일정 불확실) |
| **AI 서비스** (이 프로젝트에만 있는 선택 지점) | Claude API, 공식 SDK로 **서버에서만** 호출. API 키는 환경 변수 | 비정형 글에서 값을 뽑는 일은 규칙으로 못 한다. 이미지(캡처)도 같은 호출로 읽을 수 있어 별도 OCR 부품이 필요 없다. 모델 이름·호출 방식은 7주차에 정한다 | 브라우저에서 직접 호출(키 노출), OCR 라이브러리 + 규칙(표현 다양성을 못 따라감), 오픈소스 모델 직접 운영(노트북에서 무거움) |

> `[팀 확인]` 두 칸(클라이언트·서버 기술)은 팀원이 "이미 써 본 것"을 말하면 그 자리에서 확정된다. 나머지 다섯 칸은 비기능 요구사항에서 따라 나온 것이라 팀 기술과 무관하다.

## STEP 3. 데이터 목록

화면 명세표의 "보여줄 정보" 줄을 모아 묶었다. 세부 설계(열 이름·형식)는 10주차에 한다.

| 덩어리 | 들어가는 정보 | 어느 화면에서 나왔나 | 다른 덩어리와의 관계 |
|---|---|---|---|
| **공연** | 이름, 일시, 장소, 종류(공연/스포츠: 신고센터 링크 선택용) | ① 공연 선택, ⑤ 공연 줄 | 정가 등급 여러 개, 규정 여러 개를 가짐. 이번엔 1건 |
| **정가 등급** | 좌석 등급 이름, 1장당 정가, 출처 URL, 확인 날짜 | ⑤ 정가표, ③ 카드 "공식 안내" 문장 | 공연 하나에 속함 |
| **규정** | 규정 종류(본인 확인 필수 / 양도 금지 / 캡처 입장 불가 / 현장 수령 필수 / 기타), 공식 문장, 출처 URL, 확인 날짜 | ⑤ 규정표, ③ 카드 "공식 안내"·"출처" | 공연 하나에 속함 |
| **검사 요청** (저장하지 않음, Must) | 공연, 원문(연락처 지운 것) 또는 이미지, 추출값(1장당 가격·좌석·수량·전달 방식·선입금 여부), 근거 구절, AI 상태 | ①②③ | 요청 한 번에만 존재. Must에서는 DB에 쓰지 않는다(ADR 2) |
| **확인사항** (계산 결과, Must는 저장 안 함) | 종류, 심각도 라벨(정보/주의/확인 필요), 판매글 구절, 공식 문장, 출처 URL·확인 날짜, 쉬운 말 설명 | ③ 카드 | 검사 요청 하나에 0개 이상. 공식 문장은 정가 등급 또는 규정에서 온다 |
| **(Should) 검사 기록** | 검사 요청 + 확인사항 + 검사 일시 + 연락처 해시(원문 없음) | ④ 제보 근거 정리, "같은 연락처 반복" | 공연 하나에 속함. 같은 해시끼리 묶임 |

> 관리자 비밀번호는 데이터가 아니라 환경 변수다. 회원·세션 덩어리는 없다.

## STEP 4. API 목록

| 화면의 행동 | 요청 이름 | 서버가 확인할 것 | 돌려주는 것 |
|---|---|---|---|
| ① 공연 선택(화면 열림) | 공연 조회 | 없음 (누구나) | 공연 1건 + 정가 등급 + 규정 (출처·날짜 포함) |
| ① "이 판매글 확인하기" | 판매글 추출 | 글 또는 이미지 중 하나 이상 / 글 5,000자 이하 / 이미지는 확장자가 아니라 **파일 앞부분 바이트**로 PNG·JPG 확인, 5MB 이하 / 같은 접속에서 분당 10회 이하(AI 비용 보호) | 추출값 + 근거 구절 + AI 상태(ok/fallback). 연락처는 응답에 넣지 않음 |
| ② "공식 안내와 비교하기" | 비교(확인사항 계산) | 공연 존재 / 가격 또는 전달 방식 중 하나 이상 / 가격은 0 이상 정수, 전달 방식은 선택지 5개 중 하나, 수량은 1 이상 정수 / 좌석 등급이 정가표에 없으면 "정가 대조 불가"로 처리(오류 아님) | 확인사항 목록(0개 이상) + 요약 문장 + 고정 문구 |
| ③ "공식 안내 원문 보기" | 없음 | 서버 요청 없음. 응답에 들어 있던 출처 URL을 새 창으로 연다 | |
| ⑤ 관리자 화면 열림 | 관리자 공연 데이터 조회 | **관리자 비밀번호** | 공연 + 정가 등급 전체 + 규정 전체 |
| ⑤ "수정 내용 저장" | 관리자 공연 데이터 저장 | **관리자 비밀번호** / 출처 URL은 http(s)로 시작 / 정가는 0 이상 정수 / 등급 이름 중복 없음 / 규정 종류는 5개 중 하나 / 확인 날짜 형식 | 저장된 데이터 전체 (화면이 그대로 다시 그림) |
| ③ "제보 자료 만들기" (Should) | 검사 기록 저장·조회 | 연락처는 해시만 저장, 응답에 원문·해시 없음 | 기록 번호 → ④ 화면 데이터 |
| ③ 지문 줄 (Should) | 같은 연락처 집계 | 해시 일치만 묶음 | "다른 글 N건" 숫자만 |

> 모든 응답은 `{ ok, data, error }` 한 모양으로 통일한다(2주차 공통 패턴). 실패 메시지는 사람이 읽을 수 있는 한국어이고, 서버 내부 경로나 오류 더미는 응답에 넣지 않는다.

## STEP 5. 결정 기록 (ADR)

### ADR 1. 서버·클라이언트 기술을 무엇으로 할 것인가

| 항목 | 내용 |
|---|---|
| **결정 제목** | 서버와 클라이언트 기술 선택 |
| **상황** | 해커톤, 실제 개발은 2명이 될 가능성이 높음. AI가 코드 대부분을 만들지만 사람이 읽고 고쳐야 함(팀 규칙 3). 7주차 수업이 "오늘 정한 서버 기술"로 진행됨 |
| **선택지** | 1) 1학기에 배운 서버 기술(Spring Boot) + 팀이 아는 프론트 2) Node.js + React 3) 팀원마다 익숙한 것 |
| **결정** | **`[팀 확인]`** 기준만 확정: ① 팀 전원이 이미 써 본 것 ② 1학기에 배운 것을 안 쓸 이유가 없으면 그것 ③ 하나로 통일. 가안은 1)이며, 팀이 Node.js를 더 잘 쓰면 2) |
| **이유** | 6주차 "지루한 기술을 골라라". 막혔을 때 찾아볼 자료와 물어볼 사람이 있어야 한다. AI SDK는 Java·Node 모두 공식 제공이라 기술 선택에 영향이 없다 |
| **감수한 단점** | 가장 빠른 기술이 아닐 수 있다. 대신 발표 전날 안 돌아갈 확률이 낮다 |
| **결정한 사람 (A)** | 서버 담당 (팀 확인 뒤 기록) |

### ADR 2. 검사 결과와 이미지를 저장할 것인가 (개인정보)

| 항목 | 내용 |
|---|---|
| **결정 제목** | 판매글·캡처·검사 결과를 서버에 남길 것인가 |
| **상황** | 판매글에는 전화번호·계좌·오픈채팅 링크가 들어 있다. 기획서 Won't: 판매자 신원 공개 금지, 실제 사람 글 사용 금지. Must 흐름(①②③)은 결과를 다시 볼 필요가 없다. Should(제보 누적)는 저장이 필요하다 |
| **선택지** | 1) 아무것도 저장하지 않음 2) 원문 그대로 저장 3) 연락처를 지운 원문 + 연락처 해시만 저장 |
| **결정** | **Must: 1) 저장하지 않음.** 이미지는 메모리에서 AI에 보내고 버린다. 원문은 AI에 보내기 전에 연락처 패턴을 지운다. **Should에서 3)으로 확장**: 지운 원문 + 해시(비밀 솔트)만 저장, 원문 연락처는 어디에도 쓰지 않는다 |
| **이유** | 저장하지 않으면 지킬 것도 없다. 개인정보 장표가 "원문·이미지 미저장" 한 줄로 끝난다. 사진 저장 위치·보관 기간·삭제 스크립트 결정이 통째로 사라진다 |
| **감수한 단점** | ③ 화면을 새로고침하면 결과가 사라진다(다시 검사하면 된다). Should를 붙일 때 저장 코드를 추가해야 하므로, 검사 로직과 저장 로직을 처음부터 분리해 둔다 |
| **결정한 사람 (A)** | 서버 담당 |

### ADR 3. 어디에 올려서 시연할 것인가

| 항목 | 내용 |
|---|---|
| **결정 제목** | 배포 위치 |
| **상황** | 발표 당일 안 돌아가는 것이 최대 위험(기획서 위험 6). 동시 사용자 10명 이하. 발표장 인터넷은 믿을 수 없다. 심사 기기에서 직접 접속할지는 미정 |
| **선택지** | 1) 팀 노트북에서 서버 1개 실행 2) 클라우드 무료 티어 3) 학교 서버 |
| **결정** | **1)** 노트북에서 한 명령으로 실행. 화면 파일·DB 파일·공연 데이터 파일이 모두 같은 폴더에 있다. 외부 접속이 꼭 필요해지면 2)를 **추가**(대체가 아님) |
| **이유** | 인터넷이 끊겨도 AI 호출만 실패하고 나머지는 동작(목표 3). 무료 티어는 잠들어 있다 첫 접속이 느려 시연 중 멈출 수 있다 |
| **감수한 단점** | 심사위원이 자기 기기로 접속하려면 같은 와이파이가 필요하다. 그래서 시연 영상 백업을 둔다(기획서 위험 6) |
| **결정한 사람 (A)** | 서버 담당 |

## 부록 A. AI 제안에서 일부러 뺀 것

6주차 "AI는 과하게 설계한다"에 따라, 흔히 제안되는 상자 중 이 규모에 필요 없는 것을 적어 둔다. 누군가(사람이든 AI든) 다시 넣자고 하면 이 표를 보여 준다.

| 흔한 제안 | 뺀 이유 |
|---|---|
| 프론트 서버와 API 서버 분리 | 서버 1개가 화면 파일을 같이 주면 된다. 분리하면 설정·주소·CORS 문제가 하나 더 생긴다 |
| 캐시 서버(Redis 등) | 동시 사용자 10명. 같은 글을 두 번 넣을 때의 AI 비용은 서버 메모리의 작은 표로 충분하다(필요해지면) |
| 대기열·메시지 브로커 | AI 호출 한 번이 몇 초. 사용자가 그냥 기다리면 된다(② 로딩 상태) |
| 외부 클라우드 DB | 기획서에서 버림. 파일 하나로 충분 |
| 이미지 저장소 | 이미지를 저장하지 않기로 했다(ADR 2) |
| 회원·세션·외부 인증 | 팬 로그인 없음. 관리자는 비밀번호 1개 |
| 마이크로서비스 | 팀 2~4명, 서비스 1개 |
| 공연 공지 자동 수집기 | 기획서에서 확장으로 뺌. 공연 1건은 손으로 |
